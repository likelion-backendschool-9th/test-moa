# 프로젝트 등록·조회·수정과 모집 작성 API (#92)

개발자가 프로젝트를 등록·조회·수정하고, 프로젝트에 모집글을 작성하는 API. 도메인 전체에서 정한 것과 데이터 구조는 [README.md](README.md), 엔티티는 [entities.md](entities.md)에 있다.

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`는 백엔드 테스트와 1:1이고(`@DisplayName("#92-S…")`), `[직접]`은 사람이 로컬 DB로 확인한다.

## 1. 프로젝트·모집 작성 API (#92-R1)

주소는 WBS를 따르고 `/api/v1`로 통일한다. 주소 변수는 팀 결정(11-06)대로 나눈다: 백엔드 API는 DB의 id(`{projectId}`, `{recruitmentId}`)로 통일하고, 프론트 페이지 URL은 key(`{projectKey}`)로 남겨 둔다. 지금 프론트 key 값은 id와 같다. slug는 필요해지면 그때 더한다.

| WBS | 동작 | API | 성공 |
| --- | --- | --- | --- |
| 5.3 | 내 프로젝트 목록 | `GET /api/v1/developer/projects` | 200 |
| 5.4 | 프로젝트 등록 | `POST /api/v1/developer/projects` | 201 |
| 5.5 | 프로젝트 정보 조회 | `GET /api/v1/developer/projects/{projectId}` | 200 |
| 5.6 | 프로젝트 모집 건 목록 조회 | `GET /api/v1/developer/projects/{projectId}/recruitments` | 200 |
| 5.7 | 프로젝트 수정 | `PUT /api/v1/developer/projects/{projectId}` | 200 |
| 5.9 | 테스트 모집 작성 | `POST /api/v1/developer/recruitments` (본문의 `projectId`) | 201 |

- 프로젝트 항목은 ERD 기준으로 이름·설명·대표 이미지이고, 유형과 접속 링크는 모집글에 있다. WBS를 이 기준으로 고친다. 정원과 모집 인원은 없다(#78)
- 5.8 모집 작성 정보는 WBS에서 빠졌다. 작성 화면의 보상 안내 값을 어디서 받을지는 보상액 담당과 정한다
- 인증과 실패 응답은 #88을 쓴다: 회원 id는 토큰의 `@AuthenticationPrincipal Long userId`, 실패는 `BusinessException`과 `ApiResponse.fail`
- 값끼리 비교한 결과도 칸별로 알리도록 `BusinessException`에 `fields`를 더했다. 기존 생성자의 동작은 그대로다
- 구조는 다른 API와 같다: Controller → Service 인터페이스 → `impl` → Repository, DTO는 `domain/dto`
- 요청 값 검사와 문구는 프론트 `validateProjectForm`, `validateRecruitmentForm`과 맞춘다. 모집 인원은 #78에서 프론트에서도 빠졌다
- 프론트 값 변환: 선정 방식 `firstCome` ↔ `FIRST_COME`, `selection` ↔ `MANUAL`, 유형 `web` ↔ `WEB`
- 프로젝트 이름은 요청과 응답에서 `name`이고 엔티티에서는 `title`이다
- 날짜: 요청은 `YYYY-MM-DD`로 받아 한국 시간 기준 오늘과 비교하고, 그날 23:59:59로 저장한다. 오늘을 모집 마감일로 고를 수 있다
- 응답의 `status`는 프론트 상태 이름(`recruiting`, `testing`, `closed`, `cancelled`)이다. 취소만 저장된 값을 쓰고 나머지는 마감일로 계산한다
- 유형: 지금은 `WEB`만 받는다. `types` 행은 처음 쓸 때 만든다. 앱 시작 때 만들면 테이블이 없는 환경에서 앱이 뜨지 못하기 때문이다
- 선발형은 `SubscriptionChecker`로 구독 회원만 쓴다. 화면처럼 칸 오류(400)로 알린다
- 보상액과 구독 모집 표시는 저장 위치가 정해지지 않아 이번 응답에 넣지 않았다
- 이미지는 세 가지로 나눈다(11-06 결정). 이번 API는 세 가지 모두 URL로 받고, 실제 파일 업로드는 이미지 저장소가 정해지면 붙인다

| 이미지 | 저장 위치 | 어디서 등록 | 어디에 보이나 |
| --- | --- | --- | --- |
| 프로젝트 대표 이미지 | `projects.image_url` | 프로젝트 등록·수정 | 프로젝트 상세, 모집글 상세 이미지 띠의 첫 번째 |
| 모집글 이미지 | `recruitment_images` (`sortOrder`) | 모집 작성 | 모집글 상세 이미지 띠에서 대표 이미지 다음, 보낸 순서대로 |
| 테스트 항목 이미지 | `test_item_images` (`sortOrder`) | 모집 작성의 항목마다 | 모집글 상세의 각 테스트 항목 아래 |

- 프론트는 아직 모집 작성 폼에 모집글 이미지 칸이 없고, 모집글 상세 이미지 띠는 대표 이미지 뒤에 테스트 항목 이미지를 잇는다(#63-S9). 이 결정에 맞춰 폼 칸을 더하고 #63-S9를 고친다

| 입력 | 필수 | 한도 |
| --- | --- | --- |
| 프로젝트 이름 | 필수 | 50자 |
| 프로젝트 설명 | 선택 | 2000자 |
| 대표 이미지 URL | 선택 | 1개 |
| 모집글 제목 | 필수 | 50자 |
| 모집 설명 | 필수 | 200자 |
| 접속 링크 | 필수 | `http://` 또는 `https://`로 시작 |
| 모집 조건 | 선택 | 500자 |
| 모집글 이미지 URL | 선택 | 10개 |
| 테스트 항목 | 필수 | 1~10개, 이름 50자(필수), 설명 300자(선택), 필수 여부(필수), 이미지 URL 5개 |

| 상황 | 상태 | `error.code` |
| --- | --- | --- |
| 입력값 오류 | 400 | `INVALID_INPUT` (`error.fields`에 칸별 문구) |
| 로그인하지 않음 | 401 | `UNAUTHORIZED` |
| 없는 프로젝트, 다른 회원의 프로젝트 | 404 | `NOT_FOUND` |

테스트는 다른 컨트롤러 테스트와 같이 `@SpringBootTest`, `MockMvc`, 실제 DB로 돈다.

#92-S1 프로젝트 등록 [테스트]
- Given 이름만 적은 요청
- When  등록한다
- Then  201이고 프로젝트 ID를 돌려준다. 설명과 이미지는 null이다

#92-S2 내 프로젝트 목록 [테스트]
- Given 프로젝트 2개, 그중 하나에 모집 중·지난·취소한 모집글
- Then  내 프로젝트만 최신순으로 오고, 모집 수는 2, 모집 중인 수는 1이다. 취소한 모집은 세지 않는다. 프로젝트가 없으면 빈 배열이다

#92-S3 프로젝트 상세 [테스트]
- Then  이름, 설명, 대표 이미지, 등록일, 모집 수가 온다

#92-S4 프로젝트 수정 [테스트]
- When  이름, 설명, 대표 이미지를 바꿔 보낸다
- Then  바꾼 값이 돌아온다. 이미지를 null로 보내면 지워진다

#92-S5 찾을 수 없음 [테스트]
- Given 없는 프로젝트, 또는 다른 회원의 프로젝트
- When  조회, 수정, 모집 작성
- Then  404 `NOT_FOUND`이고 저장하지 않는다. 다른 회원의 프로젝트가 있는지 알려 주지 않는다
- Given 토큰이 없다
- Then  401이다

#92-S6 모집 작성 [테스트]
- Given 내 프로젝트, 올바른 요청, 항목 2개(이미지 있음·없음)
- When  작성한다
- Then  201이고 모집글, 유형 1줄, 항목 2줄, 항목 이미지가 저장된다. 항목 순서와 이미지 순서는 요청 순서다

#92-S7 함께 저장되거나 함께 실패 [테스트]
- Given 항목 저장이 실패한다
- Then  실제 DB에 모집글도 남지 않는다

#92-S8 일정과 링크 검사 [테스트]
- When  모집 마감일이 어제, 제출 마감일이 모집 마감일과 같거나 이르다, 접속 링크가 `ftp://`
- Then  각각 400이고 해당 칸의 오류가 온다. 저장하지 않는다

#92-S9 오늘 마감은 허용 [테스트]
- When  모집 마감일이 오늘(한국 시간)
- Then  저장되고 마감 시각은 오늘 23:59:59다

#92-S10 글자 수와 개수 [테스트]
- When  위 표의 한도를 넘거나, 필수 값이 비었거나, 항목이 0개 또는 11개, 이미지가 6개
- Then  400이고 해당 칸의 오류가 온다

#92-S11 유형과 선정 방식 [테스트]
- When  유형이 `web`이 아니거나, 선정 방식이 정해진 값이 아니거나, 구독하지 않은 회원이 `selection`을 고른다
- Then  400이고 해당 칸의 오류가 온다
- When  구독 회원이 `selection`을 고른다
- Then  `MANUAL`로 저장한다

#92-S12 실제 DB에서 저장 흐름 [직접]
- Given 빈 로컬 DB
- When  등록, 모집 작성, 모집 건 목록 조회를 차례로 부른다
- Then  앞에서 저장한 값이 조회된다

#92-S14 프로젝트 모집 건 목록 [테스트]
- Given 프로젝트에 모집글 2개, 확정 1명과 대기 1명이 있는 모집글
- Then  모집글이 최신순으로 오고, 확정 수는 확정만 센다. 상태와 선정 방식은 프론트 이름이다

#92-S13 유형은 처음 쓸 때 만든다 [테스트]
- When  모집글을 두 번 작성한다
- Then  `WEB` 행은 하나다

#92-S15 모집글 이미지 [테스트]
- Given 모집글 이미지 URL 2개를 담은 요청
- When  작성한다
- Then  `recruitment_images`에 보낸 순서대로 `sortOrder` 0, 1로 저장된다
- When  이미지 없이 작성한다
- Then  저장되고 모집글 이미지는 없다
- When  11개를 보내거나 빈 주소가 섞여 있다
- Then  400이고 `imageUrls`(또는 `imageUrls[n]`) 칸의 오류가 온다. 저장하지 않는다

## 가정 (확인 필요)
팀 결정이나 이슈에 없어서 구현하며 정한 것이다. 확인되면 [README.md](README.md#정한-것)로 옮긴다.

| # | 정한 것 | 이유 | 영향 |
| --- | --- | --- | --- |
| 1 | 마감일은 한국 시간 그날 23:59:59로 저장한다 | 요청은 날짜만 오고 컬럼은 날짜+시각이다 | 마감일 당일 지원 가능 여부와 "테스트 중"으로 넘어가는 시각. **팀 확인 필요** |
| 2 | 모집 상태는 취소만 저장하고 나머지는 마감일로 계산한다 | 프론트가 같은 방식이다 | 공개 목록(#113)·지원 API도 같은 계산을 써야 한다. **팀 확인 필요** (README 아직 정하지 않은 것 3) |
| 3 | 응답의 상태·선정 방식은 프론트 이름(`recruiting`, `firstCome`)으로 준다 | 프론트 연결 때 변환을 없앤다 | 프론트 연결 담당과 맞춘다 |
| 4 | 구독하지 않은 회원의 선발형은 400 칸 오류(`selectionMode`)다. `SUBSCRIPTION_REQUIRED`(403)를 쓰지 않는다 | 화면이 칸 아래에 오류를 보여 준다 | 고치기 쉽다 |
| 5 | `types`의 `WEB` 행은 처음 쓸 때 만든다 | 앱 시작 때 만들면 테이블이 없는 환경에서 앱이 뜨지 못한다 | 스키마 관리 도구를 정하면 초기 데이터로 옮긴다 |
| 6 | `BusinessException`에 칸별 오류 `fields`를 더한다 | 값끼리 비교한 결과도 칸별로 알린다. 기존 생성자 동작은 그대로다 | 공통 코드라 다른 담당도 쓸 수 있다 |
| 7 | 프로젝트 수정은 보낸 값으로 모두 바꾼다(PUT). 설명·이미지를 비우면 지운다 | WBS가 PUT이고 프론트 수정 폼이 전체를 보낸다 | 고치기 쉽다 |
