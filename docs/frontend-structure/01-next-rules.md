## 1.1 Next가 정하지 않은 것: 폴더 배치

Next는 프로젝트 파일을 어떻게 나누고 어디에 둘지 정하지 않는다.

> Next.js is **unopinionated** about how you organize and colocate your project files. (`구조:190`)

대신 흔한 전략 세 가지를 예로 들고, 하나를 골라 프로젝트 전체에서 일관되게 쓰라고 한다(`구조:319`).

| 전략 | 문서 설명 | 줄 |
| --- | --- | --- |
| A. `app` 밖에 둔다 | 앱 코드를 프로젝트 최상위 공용 폴더에 두고, `app`은 라우팅만 한다 | `구조:325` |
| B. `app` 안 최상위 폴더에 둔다 | 앱 코드를 `app` 최상위의 공용 폴더에 둔다 | `구조:337` |
| C. 기능이나 라우트별로 나눈다 | 전역 공유 코드는 위에 두고, 특정 라우트용 코드는 그 라우트 세그먼트로 나눈다 | `구조:349` |

`components`, `lib` 같은 폴더 이름도 예시일 뿐이고 프레임워크에서 특별한 뜻은 없다(`구조:321`). `src` 폴더도 선택 사항이다. 앱 코드와 설정 파일을 나누는 용도다(`구조:307`). `create-next-app`의 추천 기본값은 `src`를 쓰지 않는 것이지만(`설치:89`), 쓰겠느냐고 묻는 질문은 남아 있다(`설치:101`).

정리하면, 다음 질문들은 Next 문서로 답이 나오지 않는다. 팀이 정해야 한다.

- 컴포넌트를 `app` 안에 둘지 밖에 둘지
- 폴더 이름(`components`, `features`, `lib`)
- `src`를 쓸지

**지금 코드와의 관계.** `frontend/README.md`는 전략 A를 골랐다("app/ 라우트. 데이터를 불러와 도메인 컴포넌트를 조립만 한다"). 전략 A 자체는 Next 문서가 인정하는 방식이다. 그래서 문제는 "A를 골랐다"가 아니라, A를 어떤 기준으로 나눴느냐에 있다. 이 내용은 [2. 점검 결과](02-audit.md)에 있다.

## 1.2 Next가 정한 것: 파일 규칙과 그 효과

아래는 Next가 정해 둔 규칙이다. 따르지 않으면 동작이 달라지거나 문서가 피하라고 하는 방식이 된다.

| 번호 | 규칙 | 근거 | 지금 코드 |
| --- | --- | --- | --- |
| N1 | `app` 안의 폴더는 `page`·`route` 파일이 있어야 공개 라우트가 된다. 그래서 다른 파일을 라우트 폴더 안에 함께 둬도 안전하다 | `구조:245` | 라우트 폴더 안에 둔 컴포넌트가 없다(0개). 전략 A라서 문제는 아니다 |
| N2 | `_`로 시작하는 폴더는 라우팅에서 빠진다. UI 로직과 라우팅 로직을 나누는 데 쓴다 | `구조:261`, `구조:273` | `_og` 1개(OG 글꼴)뿐이다 |
| N3 | `(이름)` 폴더는 URL에 들어가지 않는 경로 그룹이다. 사이트 구역별로 라우트를 묶거나, 일부 라우트에만 레이아웃을 줄 때 쓴다 | `구조:288`, `구조:300`, `구조:303`, `구조:383` | `my/(account)` 1개를 쓴다. 계정 메뉴를 일부 마이페이지에만 주려는 용도라 문서 용법과 같다 |
| N4 | 경로 그룹마다 `layout`을 두면 URL 구조가 같아도 레이아웃을 다르게 줄 수 있다. 이 레이아웃은 상위 앱 레이아웃 안에 들어간다 | `구조:371` | 쓰지 않는다. 채팅방은 `HideFooter`로 푸터를 숨긴다(→ [2. 점검 결과](02-audit.md) F4) |
| N5 | 서로 다른 그룹의 라우트가 같은 URL로 풀리면 오류다 | `그룹:31` | 해당 없음 |
| N6 | 레이아웃은 이동할 때 다시 그려지지 않아서 `pathname`을 받지 않는다. 현재 경로가 필요하면 클라이언트 컴포넌트에서 `usePathname`으로 읽는다 | `layout:240` | 운영자 탭(`AdminShell`)은 페이지가 `path`를 넘긴다. 헤더·계정 메뉴는 클라이언트에서 `usePathname`을 쓴다. 규칙에 맞다 |
| N7 | 같은 이유로 레이아웃에서 하는 인증 검사는 이동할 때마다 돌지 않는다. 검사는 데이터 원천이나 조건부로 그리는 컴포넌트 가까이에서 한다 | `인증:1358`, `인증:1362` | 레이아웃에서 인증 검사를 하지 않는다. 페이지와 데이터 함수(`requireAdmin`, `requireMember`, `getProfile` 등)에서 한다. 규칙에 맞다 |
| N8 | 페이지의 인증 검사는 그 안의 서버 액션까지 보호하지 않는다. 액션 안에서 다시 확인한다 | `보안:339` | 액션 8개 파일 모두 직접 또는 데이터 함수(`assertAdmin`, `roomMember`, `getProfile`)를 거쳐 다시 확인한다. 로그인·가입 액션은 확인할 세션이 없다. 규칙에 맞다 |
| N9 | 새 프로젝트에는 데이터 접근 계층(DAL)을 권한다. 서버에서만 돌고, 권한을 확인하고, 필요한 값만 돌려준다. 방식은 하나로 정하고 섞지 않는다 | `보안:58`, `보안:27`, `보안:399` | 기능마다 `api.ts`(`import "server-only"`)가 데이터 접근을 맡는다. 방향은 맞다. 다만 같은 역할의 파일이 `api.ts`·`service.ts`·`users.ts`·`reviews.ts`로 이름이 갈린다(→ F7) |
| N10 | 서버 전용 코드는 `server-only`로 표시해 클라이언트에서 실행되지 않게 한다 | `보안:245` | `server-only` 22개 파일. 쿠키를 읽는 데이터 파일은 모두 표시돼 있다. 목업(`mock.ts`) 7개에는 표시가 없지만 `api.ts`만 import하므로 지금은 새지 않는다 |
| N11 | 클라이언트 컴포넌트가 import하는 모듈은 클라이언트 번들에 들어간다. 서버 컴포넌트를 `children`으로 넘기면 들어가지 않는다 | `서버·클라:182`, `서버·클라:304` | `"use client"` 34개 파일. 클라이언트 파일이 `service.ts`(server-only)를 부르는 곳은 `import type`뿐이라 안전하다 |
| N12 | `error` 파일은 클라이언트 컴포넌트여야 한다 | `error:21` | `error.tsx`가 하나도 없다. 오류가 나면 Next 기본 오류 화면이 뜬다(→ F9) |
| N13 | 서버 컴포넌트는 데이터를 원천에서 직접 가져온다. 자기 Route Handler를 거치지 않는다 | `BFF:879` | Route Handler는 소셜 로그인 콜백(`app/auth/callback/[provider]/route.ts`) 하나다. 이 핸들러는 소셜 제공자가 브라우저를 돌려보내는 주소이고, 서버 컴포넌트가 부르지 않는다. 서버 컴포넌트는 `api.ts`→`lib/backend.ts`로 Spring을 바로 부른다. 규칙에 맞다 |
| N14 | `proxy.ts`는 `app`과 같은 높이에 둔다(`src`를 쓰면 `src` 안) | `proxy:23` | `src/proxy.ts`. 규칙에 맞다 |
| N15 | 페이지 단위 전역 스타일은 Activity로 숨겨진 페이지에서 새어 나올 수 있으니, 숨겨질 때 끈다 | `UI상태:285` | `HideFooter`가 이 방법을 그대로 쓴다. 구현은 문서대로다. 다만 이 우회가 필요해진 원인은 N4를 쓰지 않은 데 있다(→ F4) |

## 1.3 요약

- Next 규칙 위반은 없다. 라우팅, 서버·클라이언트 경계, 인증 재확인, 데이터 접근, `proxy` 위치는 문서와 맞는다.
- 다만 Next가 주는 정리 도구 세 가지(라우트 폴더 안에 두기 N1, 비공개 폴더 N2, 경로 그룹 레이아웃 N4)를 거의 쓰지 않는다. 그 결과, 라우트 하나만 쓰는 코드가 모두 `features`로 갔고(F1), 푸터를 숨기는 우회 코드가 생겼다(F4).
- 폴더 배치는 Next가 정하지 않는다. 그래서 배치가 맞는지는 Next 문서가 아니라 팀이 정한 규칙과 실제 사용처로 판단해야 한다. [2. 점검 결과](02-audit.md)는 그 사용처를 스크립트로 계산한 결과다.
