# 프론트엔드 구독 관리 (`/my/subscription`)

백엔드: [결제·구독·크레딧 백엔드](../../backend/payment/README.md)

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`만 e2e 테스트와 1:1이고, `[테스트: 파일 번호]`는 그 테스트가 대신 확인한다. `[명령]`은 명령 한 번, `[직접]`은 사람이 화면을 보고 확인한다. (고침 #56)

## 한눈에
- 끝나면: `/my/subscription`에서 내 구독 상태(구독 중이면 만료일과 남은 날, 아니면 미구독)와 구독 상품의 목업 가격(30일 10,000원 / 9,000 크레딧), 구독 결제에 쓸 수 있는 크레딧을 본다. 혜택 비교 표는 두지 않는다(혜택은 결제 안내의 "혜택 보기"로 가는 공개 소개 `/subscription`의 카드에서 본다). 구독 중이면 만료 뒤 바뀌는 점도 본다. (고침 10-31: 가격 미정 안내 → 목업 가격. 고침 #76: 비교표를 뺌)
- 11-02 추가: 결제 안내의 주 버튼 "구독하기"(구독 중이면 "구독 연장하기")로 `/my/subscription/checkout`에 가서 상품과 결제 수단(크레딧·현금)을 고르고 시연용으로 결제한다 (R196~R199, S533~S543)
- 결정 필요: 목업 가격 값 (아래 가정의 기본값으로 갈지)
- 규모: 5단계, 약 2~3시간

## 맥락
- `/my/subscription`은 로그인한 회원의 구독 관리 화면이다. 마이페이지 메뉴 "구독", 대시보드 구독 카드의 "구독 관리"가 여기로 온다. 프로젝트 분석·대시보드의 "구독 알아보기"는 공개 소개(`/subscription`, `docs/frontend/payment/subscription-intro.md`)로 간다 `(고침 #76: 구독 알아보기는 공개 소개 페이지로)`.
- 구독은 계정 단위다. 개발자와 테스터는 한 계정이라 화면을 역할로 나누지 않는다. 구독 혜택은 모집 글을 올리는 쪽(개발자 활동)에 붙는다.
- 구독 가격·주기·크레딧 우대율은 기획에서 미정이다 (spec.md 3장). 화면은 목업 가격으로 만들고, 정해지면 목업 값만 바꾼다 (10-31 사용자 결정).
- 구독 상품은 지금 하나다. 나중에 늘어날 수 있어서 상품은 목록 데이터로 두고, 화면은 목록을 그린다.
- 백엔드는 고려하지 않는다. 데이터는 목업이다. (고침 #203: `AUTH_MODE=backend`에서는 구독 상태·플랜·결제 가능 크레딧을 서버에서 읽는다. 아래 "백엔드 연결")

정한 것 (11-02)
- 주소는 구독 관리 아래 `/my/subscription/checkout`이다 (출금 신청 `/my/credits/withdrawals`와 같은 구조, `docs/page-urls.md`에서는 후보).
- 결제 수단은 크레딧·현금 둘 다. 크레딧이 모자라면 크레딧 칸을 막고 모자란 양을 알리며, 현금은 시연이라 바로 결제된 것으로 본다.
- 구독 중이면 연장이다. 지금 만료일부터 상품 기간만큼 늘어난다. 만료가 지난 뒤 결제하면 결제 시각부터다.
- 만료일은 결제할 때 계산해 결제 기록에 고정한다. 결제 기록이 있으면 마지막 결제의 만료일을 쓰고, 조회 시각 기준인 목업 만료일은 쓰지 않는다. 그래야 시간이 지나며 남은 기간이 줄고 만료된다 (리뷰 반영, S542).
- 결제 기록 쿠키는 가장 늦은 만료일 + 30일까지 남긴다. 여러 번 연장한 기간이나 크레딧 차감 기록이 이용 기간보다 먼저 사라지지 않게 하기 위해서다 (리뷰 반영, S543). 10건을 모두 연장해도 약 1년이라 브라우저의 쿠키 수명 상한(400일) 안이다.
- 크레딧 결제는 이벤트 크레딧(가입 크레딧 등, 구독 결제 전용)을 먼저 쓰고, 모자란 만큼 적립 크레딧(테스트로 받은 크레딧)에서 뺀다. 출금 처리 중인 크레딧은 쓰지 않는다.
- 금액을 다루는 폼이라 고르는 칸과 버튼은 12px 모서리다 (DESIGN.md The Money Field Rule). 고른 칸은 바탕이 진해진다 (운영자 처리 폼과 같은 모양).
- 결제 뒤에는 구독 화면으로 돌아가 `?notice=paid`로 알린다 (참여 상세의 `?notice=submitted`와 같은 방식). 안내 문구에만 "시연용이라 실제로 결제되지 않고 이 브라우저에만 남아요"를 붙인다.
- 시연용 결제 기록은 10건까지다. 오래된 기록을 지우면 만료일과 크레딧이 함께 틀어져서, 가득 차면 더 받지 않는다.
- 클라이언트 컴포넌트 `CheckoutForm` 1개를 더한다 (고른 칸에 따라 금액·이용 기간·버튼 이름이 바뀐다). 홈 문서 S78 갱신.
- 구조: `src/lib/demo-subscription.ts`(시연용 결제 기록), `src/features/my/subscription-actions.ts`(`payForSubscription`), `src/features/my/components/CheckoutForm.tsx`, `src/app/my/(account)/subscription/checkout/page.tsx`. 결제 기록은 `features/my/api.ts`(만료일), `features/credit/api.ts`(잔액·내역), `lib/session.ts`(헤더 크레딧)가 읽는다.

## 구독 결제 백엔드 연결 (#204)
`AUTH_MODE=backend`에서 구독 결제 화면(`/my/subscription/checkout`)이 서버 결제 API를 쓴다. 번호는 `#204-S17`부터다(`#204-S1`~`S10`은 백엔드 [admin-subscription.md](../../backend/payment/admin-subscription.md), `S11`~`S16`은 [운영자 구독 관리](../admin/subscriptions.md)). 값이 없으면 목업(시연용 쿠키 결제)이다.

| 화면 값 | 서버 |
| --- | --- |
| 이용 기간(시작·끝) | `GET /api/v1/my/subscription/checkout?planId=`의 `period` |
| 결제하기 | `POST /api/v1/my/subscription/checkout` `{ planId, method }` (`method`는 `CASH`·`CREDIT`) |

크레딧 부족 안내(모자란 양)는 화면이 이미 읽은 결제 가능 크레딧(`payable-credits`)으로 계산해 크레딧 결제를 고를 수 없게 막는다. **결제 요청을 막는 검사는 서버가 한다**: 백엔드 모드에서는 폼 액션이 크레딧 부족·운영자 계정을 미리 막지 않고 서버로 보내, 서버의 거절 메시지를 그대로 보여 준다(목업 모드만 폼 액션이 검사한다). 결제 뒤 구독 화면(`/my/subscription`)은 서버의 구독 상태를 읽어 만료일에 반영한다.

#204-S17 이용 기간을 서버 값으로 본다 [직접]

## PG 결제 (#249)
`AUTH_MODE=backend`에서 결제 수단 "현금"이 카카오페이·토스페이 테스트 결제창을 거친다. 번호는 `#249-S14`부터다(`#249-S1`~`S13`은 백엔드 [pg-checkout.md](../../backend/payment/pg-checkout.md)). 크레딧 결제와 목업 모드(`AUTH_MODE`가 `backend`가 아님)는 지금과 같다.

| 화면 | 서버 |
| --- | --- |
| 고를 수 있는 결제 대행사 | `GET /api/v1/my/subscription/checkout`의 `providers` |
| 현금 결제하기 | `POST …/checkout/ready` `{ planId, provider }` → 결제창으로 이동 |
| 결제창에서 돌아옴 | `POST …/checkout/approve` `{ orderId, pgToken | paymentKey, amount }` |

- **현금을 고르면 그 아래에 결제 대행사(카카오페이·토스페이) 칸이 나온다.** 쓸 수 있는 것만 고르게 하고, 서버가 쓸 수 없다고 한 것은 흐리게 두고 "지금은 쓸 수 없어요"를 적는다. 둘 다 쓸 수 없으면 현금 결제 버튼을 막는다. 크레딧을 고르면 이 칸은 보이지 않는다.
- **카카오페이는 이동만 한다.** (고침 #252: PC는 팝업이 열려 있으면 이동하지 않고 팝업에 주소를 보낸다. 모바일은 이동) 폼 액션이 결제 준비를 부르고 서버가 준 결제창 주소로 이동한다. 모바일 브라우저(요청의 `user-agent`)면 모바일 주소, 아니면 PC 주소다.
- **토스는 브라우저가 토스페이 창을 바로 연다.** (고침 #252: PC는 우리 팝업 안에서 연다. 모바일은 지금처럼) 폼 액션이 준비 값(`orderId`, `amount`, `orderName`, `clientKey`, `customerKey`, `successUrl`, `failUrl`)을 돌려주면 폼 컴포넌트가 토스 SDK의 `payment({ customerKey })`로 `requestPayment({ method: "CARD", amount: { currency: "KRW", value }, orderId, orderName, successUrl, failUrl, card: { flowMode: "DIRECT", easyPay: … } })`를 부른다(리다이렉트 방식, 모바일에서 되는 쪽). 결제창을 여는 동안 버튼은 "결제하는 중…"이다. SDK는 npm 패키지(`@tosspayments/tosspayments-sdk`)로 넣는다(주소·버전이 고정되고 CSP를 건드리지 않는다). `easyPay` 값과 호출 모양은 구현할 때 결제창을 열어 확인한다.
- **돌아오는 주소는 `/my/subscription/checkout/result`다.** 카카오페이는 서버가 만든 승인 주소에 이미 들어 있는 `orderId` 뒤에 `pg_token`을, 토스는 `paymentKey`·`orderId`·`amount`를 쿼리로 붙여 준다. 로그인한 회원만 볼 수 있고 비로그인은 로그인 뒤 이 주소로 돌아온다. 이 페이지가 `approve`를 부르고, 성공하면 결제 완료 화면 `/my/subscription/checkout/complete?payment=<결제 id>`로 보낸다. 실패하면 이 페이지에 서버 문구와 "결제 화면으로 돌아가기" 링크를 보여 준다. 승인 요청은 서버 쪽에서 한 번만 받으므로 새로고침해도 구독이 늘지 않는다.
- **취소·실패는 결제 화면으로 돌아온다.** 안내는 버튼 옆의 작은 글씨가 아니라 카드 위쪽(제목 아래)에 테두리가 있는 눈에 띄는 칸으로 보인다(#249-S28). (고침 #252: 경고색) 서버가 거절한 이유는 지금처럼 버튼 위에 보인다. 토스 결제창을 닫아 돌아온 안내도 같은 칸이다. 카카오페이 취소·실패 주소와 토스 실패 주소는 `/my/subscription/checkout?pg=cancel`·`?pg=fail`이다. 이 값이 있으면 폼 위에 "결제를 취소했어요"·"결제하지 못했어요. 다시 시도해 주세요"를 보이고 구독은 만들어지지 않았다. 알 수 없는 `pg` 값은 무시한다.
- **금액은 화면이 정하지 않는다.** 폼의 금액 표시는 안내용이고, PG에 넘기는 금액과 승인 때 비교하는 금액은 서버가 준비 때 정한 값이다.
- **결제 완료 화면 `/my/subscription/checkout/complete`가 끝을 맺는다.** 백엔드 모드에서 크레딧 결제와 카카오페이·토스 승인이 끝나면 이리로 온다(서버가 준 결제 id가 `?payment=`로, 방금 결제했다는 표시가 `&paid=1`로 붙는다). 서버의 내 결제 이력(`GET …/payments`)에서 그 결제를 찾아 "결제가 완료됐어요", 상품·결제 수단(크레딧·카카오페이·토스페이)·결제 시각·이용 기간·결제 금액과 "구독 보기"·"마이페이지" 버튼을 보인다. 내 이력만 읽으므로 남의 결제 id는 찾지 못한다. 결제 id가 숫자(0으로 시작하지 않는 18자리 이하)가 아니거나 이력에 없으면 "결제 내역을 찾지 못했어요"와 구독 화면 링크를 보인다. 로그인한 회원만 볼 수 있다. 구독 화면의 결제 내역에서 한 건을 눌러 와도 같은 화면이 열리는데(`paid` 없음), 이때 제목은 "결제가 완료됐어요"가 아니라 "결제 내역"이다. 목업은 결제를 서버에 남기지 않아서 이 화면 없이 지금처럼 구독 화면의 `notice=paid` 안내로 끝난다(이 화면에 직접 들어오면 구독 화면으로 보낸다).
- **구독 화면(`/my/subscription`)에 "결제 내역" 칸이 있다.** 구독 상태·결제 안내 아래, "만료되면" 위에서 서버의 내 결제를 최신순으로 최근 5건 보인다(`GET …/payments`). 한 줄에 상품, 결제일·결제 수단(크레딧·카카오페이·토스페이, 예전 현금 결제는 "현금"), 결제 금액이 있고 누르면 결제 내용 화면이 열린다. 5건을 넘으면 "최근 5건만 보여요 (전체 N건)"를 적고, 결제가 없으면 "아직 결제 내역이 없어요"다. 결제 내역만 읽지 못해도 구독 화면은 열리고 이 칸만 빠진다. 목업에는 서버 결제가 없어 이 칸이 보이지 않는다. 결제 이력 전체 목록·페이지 나누기·환불 표시는 하지 않는다(환불은 범위 밖).
- 새 페이지 `/my/subscription/checkout/result`와 `/my/subscription/checkout/complete`는 `frontend/e2e/pages.ts`의 `PAGES`에 더한다(보는 역할은 결제 화면과 같은 `developer`).

## 결제 팝업 (#252)
`AUTH_MODE=backend`의 현금 결제를 PC에서 하면 카카오페이·토스페이 결제창이 팝업으로 열린다(#249는 카카오페이는 현재 창을 이동, 토스는 SDK가 연 작은 새 창). 번호는 `#252-S1`부터다. 서버(API)는 바뀌지 않고 결제 준비 응답을 어디로 쓰는지만 달라진다.

- **팝업은 결제하기를 누르는 순간 연다.** 서버 응답을 기다린 뒤에 열면 브라우저가 막는다. 그래서 누르는 순간 빈 팝업(창 이름 `moa-pay`)을 먼저 열고, 서버의 결제 준비가 끝나면 카카오페이는 결제창 주소로, 토스는 우리 화면 `/my/subscription/checkout/toss`로 보낸다. 토스 결제창 값(결제 키·금액·성공 주소 등)은 주소에 싣지 않는다. 그 화면이 열리면 원래 창에 값을 달라고 `postMessage`로 요청하고, 원래 창이 자기가 연 팝업에게만 한 번 보낸다(주소만 열어서는 다른 값으로 결제창을 띄울 수 없다). 원래 창이 없거나 5초 안에 값이 오지 않으면 "결제 정보를 받지 못했어요"를 보인다. 토스 SDK는 창 크기를 정할 수 없어서 팝업 안에서 `windowTarget: "self"`로 연다. 폼에 숨은 `popup=1`이 있으면 폼 액션이 카카오페이를 이동시키지 않고 주소를 돌려준다.
- **팝업은 원래 창의 가운데에 열린다.** 카카오페이 430×620, 토스 480×700이고 `popupFeatures`가 원래 창의 위치·크기로 계산한다(화면 밖이면 0으로 둠).
- **결과는 원래 창에서 본다.** 결제창을 거쳐 우리 화면(결제 화면, 결과 화면, 결제 완료 화면)으로 돌아온 팝업이 자기 주소를 원래 창에 `postMessage`로 알리고 닫힌다(`PopupReturn`). 원래 창은 그 주소로 이동한다. 알릴 수 있는 주소는 `/my/subscription/checkout` 아래만이다(`isPopupReturnPath`). 결제창이 원래 창과의 연결을 끊은 경우에는 같은 사이트끼리 쓰는 `BroadcastChannel`로 알린다. 원래 창이 이미 닫혔으면 아무것도 하지 않아서 팝업이 보통 화면으로 남는다. 팝업이 닫히기 전 잠깐 "결제 결과를 원래 창으로 보내고 있어요"가 화면을 덮는다.
- **팝업이 열려 있는 동안** 결제하기 버튼이 막히고 버튼 옆에 "결제창이 열려 있어요. 결제를 마치면 이 화면이 자동으로 바뀌어요."와 "결제창 앞으로 가져오기"가 보인다.
- **결과 없이 팝업이 닫히면** 원래 창에 "결제를 취소했어요"가 보인다(500ms마다 팝업이 닫혔는지 본다). 결과를 알리고 스스로 닫힌 경우는 취소가 아니다. 서버가 결제 준비를 거절하면 팝업을 닫고 서버가 준 이유만 보인다(우리가 닫은 팝업은 취소로 보지 않는다). 토스 응답이 오기 전에 빈 팝업을 닫았으면 토스 결제창을 열지 않고 취소 안내만 보인다. 결과를 받는 것은 그 팝업을 연 탭뿐이라 같은 결제 화면을 연 다른 탭은 이동하지 않는다.
- **브라우저가 팝업을 막으면** 서버에 결제를 준비시키지 않고 "팝업이 막혀 있어요. 주소창 오른쪽에서 이 사이트의 팝업을 허용한 뒤 결제하기를 다시 눌러 주세요"를 보인다. 현재 창으로 이동하지 않는다.
- **모바일 브라우저와 크레딧 결제는 지금과 같다.** 모바일은 카카오페이를 현재 창에서 이동하고 토스는 SDK 기본 방식으로 연다.
- **취소·실패 안내는 경고색이다.** 글자 `--warning`, 배경 `--warning-soft`, 테두리 `--warning`(다크 모드 값은 토큰에 있다).
- 새 페이지 `/my/subscription/checkout/toss`는 `frontend/e2e/pages.ts`의 `PAGES`에 더한다(보는 역할은 결제 화면과 같은 `developer`).

#252-S1 PC에서 카카오페이로 결제하면 원래 창 가운데에 팝업이 열린다 [직접]
- Given 일반 회원, `AUTH_MODE=backend`, PC 브라우저
- When  현금·카카오페이로 결제하기를 누른다
- Then  원래 창의 가운데에 430×620 팝업이 열리고 카카오페이 결제창(QR)이 보인다. 원래 창은 이동하지 않는다

#252-S2 팝업에서 승인하면 원래 창이 결제 완료 화면으로 간다 [직접]
- When  팝업에서 카카오페이 또는 토스페이 결제를 승인한다
- Then  팝업이 닫히고 원래 창에 "결제가 완료됐어요"가 보인다. 결제는 한 번만 승인된다

#252-S3 결과 없이 팝업을 닫으면 원래 창에 취소 안내가 보인다 [직접]
- When  팝업을 닫는다(승인·취소 없이)
- Then  원래 창에 "결제를 취소했어요"가 보이고 결제하기 버튼이 다시 눌린다

#252-S12 서버가 결제 준비를 거절하면 팝업이 닫히고 취소 안내 없이 이유만 보인다 [직접, 카카오페이 키를 틀리게 준 임시 환경에서 확인]
- Given 서버가 결제 준비를 거절한다(5초 안 재결제, 또는 카카오페이·토스가 준비를 거절해 "지금은 이 결제 수단을 쓸 수 없어요"가 오는 경우)
- Then  팝업이 닫히고 서버가 준 이유만 보이며 "결제를 취소했어요"는 보이지 않는다. 결제 시도(`payment_attempts`)는 늘지 않고 결제하기 버튼이 다시 눌린다

#252-S4 브라우저가 팝업을 막으면 허용 방법을 안내한다 [직접]
- Given 이 사이트의 팝업을 막은 브라우저
- When  결제하기를 누른다
- Then  허용 방법 안내가 보이고 결제는 준비되지 않는다(`payment_attempts`에 새 줄이 없다). 허용한 뒤 다시 누르면 팝업이 열린다

#252-S5 모바일은 현재 창에서 결제창으로 이동한다 [직접]
- Given 모바일 브라우저
- When  카카오페이로 결제하기를 누른다
- Then  팝업 없이 현재 창이 모바일 결제창으로 이동한다. 토스는 SDK 기본 방식으로 열린다

#252-S6 취소·실패 안내가 경고색으로 보인다 [직접]
- Given 결제 화면에 `?pg=cancel` 또는 `?pg=fail`로 들어오거나 팝업을 닫아 돌아온다
- Then  안내의 글자·배경·테두리가 경고색이다(라이트·다크 모두)

#252-S7 팝업이 열려 있는 동안 안내가 보이고 결제하기가 막힌다 [직접]
- Then  "결제창이 열려 있어요" 안내와 "결제창 앞으로 가져오기"가 보이고 결제하기 버튼이 막혀 있다. 팝업이 닫히면 원래대로 돌아온다

#252-S8 PC에서 토스페이로 결제하면 팝업 안에서 토스 결제창이 열린다 [직접]
- When  현금·토스페이로 결제하기를 누른다
- Then  원래 창 가운데의 팝업 안에서 토스 결제창이 열리고 창이 또 뜨지 않는다. 승인하면 #252-S2와 같다
- Given 결제 준비 응답이 오기 전에 빈 팝업을 닫는다
- Then  토스 결제창이 열리지 않고 "결제를 취소했어요"만 보인다
- Given 토스 팝업 화면 주소(`…/checkout/toss`)를 쿼리와 함께 직접 연다
- Then  결제창이 열리지 않고 "결제 정보를 받지 못했어요"가 보인다

#252-S9 팝업이 원래 창에 알릴 수 있는 주소는 결제 화면 아래 주소뿐이다 [테스트]
- `/my/subscription/checkout`(와 그 아래 한 단계 주소, 쿼리 가능)만 받는다. 다른 사이트, `//`, 다른 경로, `..`, `#`, 문자열이 아닌 값은 받지 않는다

#252-S10 팝업은 원래 창의 가운데에 열리고 화면 밖으로 나가지 않는다 [테스트]
- 위치는 원래 창의 가운데이고, 원래 창이 팝업보다 작거나 화면 왼쪽 밖이어도 음수 위치를 주지 않는다

#252-S11 원래 창이 보낸 토스 결제창 값은 모양이 맞을 때만 받는다 [테스트]
- 준비 값 7개가 모두 있고 금액이 정수·양수일 때만 결제창을 연다. 하나라도 빠지거나 금액이 이상하거나 객체가 아니면 열지 않는다

## 가정
- 화면 순서: 내 구독 → 결제 안내 → 만료되면(구독 중일 때만). 1024px 이상에서 내 구독과 결제 안내를 나란히 둔다. (고침 #76: 혜택 비교를 뺌) (배치는 구현 뒤 스크린샷으로 확인)
- 제목은 메뉴 이름과 같은 "구독"이다. URL 목록의 "구독 관리"는 페이지 종류 이름이다.
- 남은 날은 대시보드의 D-day 형식(`formatDday`)을 쓴다. 만료일은 접속 시각 +30일이다 (마이페이지 목업과 같음).
- 구독 결제에 쓸 수 있는 크레딧 = 테스트 획득 크레딧 − 출금 처리 중 + 가입 크레딧 (GLOSSARY: 가입 크레딧은 구독 결제 전용, 처리 중인 출금은 잠김). 승인 대기 보상은 넣지 않는다.
- 운영자는 구독 대상이 아니다 (마이페이지 가정과 같음).
- 혜택 문구는 spec.md 2장 표와 4장 "구독 만료"를 화면 말투로 옮긴 것이다. 보상액 수치는 쓰지 않는다. (고침 10-31: 한도는 목업 숫자)
