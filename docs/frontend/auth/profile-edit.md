# 프론트엔드 개인정보 수정 (`/my/profile/edit`)

백엔드: [회원·인증 백엔드](../../backend/auth/README.md)

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`만 e2e 테스트와 1:1이고, `[테스트: 파일 번호]`는 그 테스트가 대신 확인한다. `[명령]`은 명령 한 번, `[직접]`은 사람이 화면을 보고 확인한다. (고침 #56)

## 한눈에
- 끝나면: `/my/profile/edit`에서 이름·닉네임을 고쳐 저장하고, 현재 비밀번호를 확인한 뒤 새 비밀번호로 바꾼다. 이메일은 보이기만 한다. 입력이 틀리면 칸 아래에 이유가 보인다. 저장은 목업이라 성공 메시지만 보이고 새로고침하면 원래 값이다.
- 결정 필요: 없음 (수정 항목: 이름·닉네임 + 비밀번호 변경, 브랜치: develop에서 새로 — 10-30 확정)
- 규모: 5단계, 약 3~4시간

## 맥락
- 지금 `/my/profile/edit`은 "준비 중"이다. 마이페이지 메뉴 "개인정보 수정", 대시보드 프로필의 "개인정보 수정", 헤더·모바일 메뉴의 "내 정보"가 여기로 온다.
- 회원 정보는 이름·닉네임·이메일 세 가지다 (`features/my/types.ts`의 `Profile`). 기획서에 수정 규칙은 없다.
- 개발자와 테스터는 한 계정이다. 화면을 역할로 나누지 않는다.
- 백엔드는 고려하지 않는다. 데이터와 제출은 모두 목업이다.
- 크레딧 PR(#9)의 출금 폼 `Field` 패턴, `Button shape="field"`, `.select-field`는 쓰지 않는다 (금액 폼이 아니므로 알약 규칙). (고침 11-01: PR #9가 develop에 병합됨)

## 7. 연동된 계정 (#84)
`AUTH_MODE=backend`이면 개인정보 수정 화면 맨 아래에 "연동된 계정"이 보인다. 연동·해제는 백엔드의 `POST·DELETE /api/users/me/accounts/{provider}`, 연동 상태와 이메일은 `GET /api/users/me`의 `providers`·`accounts`를 쓴다. 목업에는 연동이 없어서 보이지 않는다. 새 주소는 없다(연동은 기존 소셜 콜백 `/auth/callback/[provider]`이 이어 받는다).

- #84-R3 구글·깃허브를 연동하거나 해제한다. 연동은 로그인과 같은 동의 화면을 거쳐 이 화면으로 돌아오고, 결과는 주소의 `linked`·`unlinked`·`accountError`(연동 실패)·`unlinkError`(해제 실패) 키로 보인다(문구는 화면이 고른다). 마지막 로그인 방법은 해제할 수 없고 "마지막 로그인 방법은 해제할 수 없어요"만 보인다. 그 밖의 해제 실패는 "연동을 해제하지 못했어요"
- #84-R5 연동은 시작한 회원에게만 붙는다. 연동을 시작할 때 회원 id를 `oauth_state` 쿠키에 두고, 돌아왔을 때 지금 로그인한 회원과 다르면 연동 API를 부르지 않고 "연동하지 못했어요"를 보인다. 로그아웃과 이메일 로그인 때 `oauth_state`를 지운다(공용 PC에서 앞 사람이 시작한 연동이 다음 사람 계정에 붙지 않게)
- #84-R4 구글·깃허브 카드 두 장이 나란히 보이고(좁은 화면은 위아래), 연동한 카드는 초록 테두리·"연동됨"과 그 계정의 이메일을 보인다. 이메일을 모르는 예전 연동 계정은 "…로도 로그인할 수 있어요"가 보이고 다음 소셜 로그인 뒤 이메일로 바뀐다(docs/backend/auth/README.md #84-R4)

#84-S24 계정 연동과 해제 [직접]
- When  깃허브 "연동하기"를 누르고 동의한다
- Then  이 화면으로 돌아와 "깃허브 계정을 연동했어요"와 "연동됨"이 보인다
- When  마지막 로그인 방법을 해제한다
- Then  "마지막 로그인 방법은 해제할 수 없어요" 안내가 보인다

#84-S32 연동을 시작한 뒤 다른 회원으로 바뀌면 연동하지 않는다 [직접]
- Given A가 개인정보 수정에서 "연동하기"를 눌러 `oauth_state`(`link`)가 생겼다
- When  A가 로그아웃한다
- Then  `oauth_state`가 지워진다
- Given 같은 `oauth_state`가 남은 채 B로 로그인했다
- When  그 state로 콜백(`/auth/callback/{provider}`)이 온다
- Then  연동 API를 부르지 않고 `/my/profile/edit?accountError=oauth`로 가서 "연동하지 못했어요"가 보인다. B의 연동은 그대로다

#84-S31 연동한 계정 카드에 그 계정의 이메일이 보인다 [직접]
- Given 깃허브를 연동한 회원, `/my/profile/edit`
- Then  깃허브 카드에 초록 테두리, "연동됨", 깃허브 계정 이메일이 보이고 구글 카드는 "연동하면 구글로도 로그인해요"와 "연동하기"다
- Then  375px에서 두 카드가 위아래로 쌓이고 긴 이메일은 칸 안에서 줄을 바꾼다

## 8. 실제 API 연결 (#84)
`AUTH_MODE=backend`이면 개인정보 수정 화면이 백엔드의 내 정보 API(`GET·PATCH /api/users/me`, `PATCH /api/users/me/password`, `POST·DELETE /api/users/me/accounts/{provider}`)를 쓴다. 값이 없으면 지금처럼 목업이다. `#84-S1~S8`은 탈퇴 화면이 쓴다. 연동된 계정은 7장이다.

- #84-R1 이름·닉네임은 백엔드에 저장한다. 닉네임 중복과 비밀번호 확인은 백엔드가 하고, 칸별 오류는 그 칸 아래, 칸이 없는 오류는 폼 위에 보인다
- #84-R2 소셜로만 가입해 비밀번호가 없는 회원은 "비밀번호 변경" 대신 현재 비밀번호 칸 없는 "비밀번호 만들기"를 본다

#84-S22 이름·닉네임 저장 [직접]
- When  이름·닉네임을 바꿔 저장한다
- Then  "개인정보를 저장했어요"가 보이고 새로고침해도 바뀐 값이다
- When  다른 회원의 닉네임으로 저장한다
- Then  닉네임 칸 아래에 "이미 쓰고 있는 닉네임이에요"가 보인다

#84-S23 비밀번호 변경과 만들기 [직접]
- When  현재 비밀번호를 틀리게 적는다
- Then  현재 비밀번호 칸 아래에 이유가 보인다
- When  맞게 바꾼다
- Then  "다른 기기에서는 다시 로그인해야 해요" 안내가 보이고 칸이 비워진다
- Given 소셜로만 가입한 회원
- Then  "비밀번호 만들기"가 보이고, 만들면 이메일로도 로그인한다
- Then  만든 뒤 새로고침 없이 같은 화면이 "비밀번호 변경"(현재 비밀번호 칸 있음)으로 바뀌고, 탈퇴 창도 확인 문구 대신 비밀번호를 받는다. 다른 탭에서 만들어 화면이 예전 상태면 "비밀번호가 이미 있어요. 새로고침한 뒤 다시 시도해 주세요"가 폼 위에 보인다

## 9. 회원 탈퇴 (#84, D안)
탈퇴로 가는 길은 두 곳이고(D안), 새 주소 없이 그 자리에서 확인 창이 열린다. 개인정보 보호법(동의 철회는 가입보다 어렵지 않게)과 전자상거래법(해지·탈퇴 방해 금지)에 맞춰 찾기 쉽게 두고, 흐린 작은 글씨로 숨기지 않는다. 새 주소가 없어서 `docs/page-urls.md`와 `PAGES`는 바꾸지 않는다.

- 진입 1: 마이페이지 홈(`/my`) 맨 아래 "계정" 카드. 이메일 주소, 로그인 방법(이메일·비밀번호, 구글, 깃허브)과 "탈퇴해도 30일 안에는 되돌릴 수 있어요" 안내, 로그아웃·회원 탈퇴 버튼. 개인정보 수정은 왼쪽 메뉴에 있어서 두지 않는다
- 진입 2: 개인정보 수정 맨 아래 "회원 탈퇴" 줄. 다른 줄처럼 왼쪽에 제목·설명, 오른쪽에 안내와 버튼
- 확인 창: 브라우저 기본 `<dialog>`. 제목 "회원 탈퇴할까요?", 안내 세 줄(30일 안에 되돌릴 수 있음, "30일이 지나면 개인정보가 전부 사라지고 되돌릴 수 없어요", "남은 12,480 크레딧은 사라져요"처럼 다른 화면과 같은 크레딧 표기), 비밀번호 칸, 취소(ghost)·탈퇴하기(strong). 진입 버튼은 보조(secondary)
- 소셜로만 가입해 비밀번호가 없는 회원(실제 로그인)은 비밀번호 대신 "탈퇴합니다"를 입력한다
- 출금 처리 중인 크레딧이 있으면 안내만 보이고 탈퇴할 수 없다. 실제 로그인에서는 크레딧 API의 `lockedBalance`로 본다
- 탈퇴하면 로그아웃하고 `/login?left=1`로 가서 "탈퇴했어요. 30일 안에 다시 로그인하면 되돌릴 수 있어요"를 보인다
  - 실제 로그인: `DELETE /api/users/me`로 30일 탈퇴 유예가 되고 모든 기기의 로그인이 끊긴다. 목업: 로그아웃만 한다
- 되돌리기(실제 로그인): 유예 중에 이메일·소셜로 로그인하면 백엔드가 되돌리기 토큰(10분)을 준다. 토큰은 주소 대신 httpOnly 쿠키에 두고 `/login?restore=1`로 간다. 로그인 화면 위에 창(`<dialog>`)이 바로 뜬다
  - 제목 "탈퇴 신청을 취소할 수 있어요"
  - 본문 "{닉네임} 님의 계정은 {삭제 예정일}에 완전히 삭제될 예정이에요. 취소하면 탈퇴 신청 전과 똑같이 이용할 수 있어요." 닉네임은 백엔드가 `error.fields.nickname`으로 준다
  - "탈퇴 취소하고 로그인"(primary)을 누르면 `POST /api/auth/restore`로 되돌리고 로그인한다
  - "다른 계정으로 로그인"·Esc·바깥 누르기로 닫으면 `/login`으로 바뀌어 다시 뜨지 않는다

#84-S1 마이페이지 홈 맨 아래 "계정" 카드에 로그인 방법과 로그아웃·회원 탈퇴가 있다 [테스트]
- Given `demo-role=tester`
- When  `/my`에 접속한다
- Then  "계정" 카드에 이메일 주소, 로그인 방법 "이메일·비밀번호"와 "로그아웃", "회원 탈퇴" 버튼이 이 순서로 있고 링크는 없다

#84-S2 개인정보 수정 맨 아래 "회원 탈퇴" 줄에 안내와 버튼이 있다 [테스트]
- When  `/my/profile/edit`에 접속한다
- Then  "회원 탈퇴" 줄이 "비밀번호 변경" 아래에 있고 "회원 탈퇴" 버튼이 있다

#84-S3 회원 탈퇴를 누르면 주소는 그대로이고 확인 창에 안내가 보인다. 취소·Esc로 닫힌다 [테스트]
- When  "회원 탈퇴"를 누른다
- Then  주소는 그대로이고 "회원 탈퇴할까요?" 창에 "30일 안에", "개인정보가 전부 사라지고", "남은 12,480 크레딧"이 보인다
- When  "취소"를 누르거나 Esc를 누른다
- Then  창이 닫힌다

#84-S4 비밀번호가 비거나 틀리면 창 안 칸 아래에 알리고 탈퇴하지 않는다 [테스트]
- When  비밀번호 없이, 또는 틀린 비밀번호로 "탈퇴하기"를 누른다
- Then  "비밀번호를 입력해 주세요" 또는 "비밀번호가 맞지 않아요"가 보이고 창과 로그인 상태가 그대로다

#84-S5 출금 처리 중인 크레딧이 있으면 탈퇴할 수 없다 [테스트]
- Given 출금을 신청해 처리 중인 크레딧이 있다
- When  확인 창을 연다
- Then  "출금 처리 중인 크레딧이 있어 지금은 탈퇴할 수 없어요. 처리된 뒤 다시 시도해 주세요"가 보이고 비밀번호 칸과 "탈퇴하기"가 없다

#84-S6 맞는 비밀번호로 탈퇴하면 로그아웃되고 로그인 화면에 안내가 보인다 [테스트]
- When  `test1234`로 "탈퇴하기"를 누른다
- Then  URL이 `/login?left=1`이고 "탈퇴했어요. 30일 안에 다시 로그인하면 되돌릴 수 있어요"가 보인다
- Then  `/my`에 접속하면 로그인으로 간다

#84-S7 진입 버튼은 보조, 창의 "탈퇴하기"는 먹색(strong), "취소"는 ghost이고 좁은 화면에서 창이 넘치지 않는다 [직접]
- 너비 375px에서 `/my`, `/my/profile/edit`의 확인 창을 연다

#84-S8 유예 중에 로그인하면 되돌릴지 묻고, 되돌리면 그대로 로그인한다 [직접]
- Given 실제 로그인에서 탈퇴한 회원
- When  같은 계정으로 이메일(또는 소셜) 로그인한다
- Then  `/login?restore=1` 위에 창이 바로 뜨고 "탈퇴 신청을 취소할 수 있어요", 닉네임과 삭제 예정일이 보인다
- When  "다른 계정으로 로그인"을 누른다
- Then  창이 닫히고 주소가 `/login`이 된다
- When  다시 로그인해 "탈퇴 취소하고 로그인"을 누른다
- Then  로그인되어 마이페이지를 쓸 수 있다. 10분이 지나 누르면 "되돌리기 시간이 지났어요. 다시 로그인해 주세요"가 보인다

#84-S25 소셜로만 가입한 회원은 확인 문구로 탈퇴한다 [직접]
- Given 실제 로그인에서 비밀번호가 없는 회원
- When  확인 창을 연다
- Then  비밀번호 칸 대신 "확인 문구" 칸이 보이고, "탈퇴합니다"가 아니면 칸 아래에 안내가 보인다

## 가정
- 화면: h1 아래 한 장의 면에 "기본 정보" 줄, 그 아래 "비밀번호 변경" 줄. 폼이 둘이고 버튼도 각자 있다 (한쪽 오류가 다른 쪽 저장을 막지 않게). 넓은 화면은 Tailwind Plus 설정 화면처럼 제목·한 줄 설명 왼쪽, 칸 오른쪽이다. (고침 10-30: 빈 공간 피드백)
- 모양: 금액 폼이 아니므로 DESIGN.md 기본 규칙(누르는 것은 알약)을 따른다. 입력 칸도 검색창과 같은 알약, 높이 48px. 새 hex·px 값은 넣지 않는다.
- 이름: 필수, 앞뒤 공백 제거 후 1~20자.
- 닉네임: 필수, 한글·영문·숫자 1~39자 (`/^[가-힣a-zA-Z0-9]{1,39}$/`, 고침 11-01: 2~12자 → 깃허브 사용자명 길이). 규칙은 `src/lib/validation.ts`에서 회원가입과 함께 쓴다. 다른 시연 회원의 닉네임("윤슬", "도현랩", 운영자 닉네임)은 사용 중으로 본다. 자기 닉네임은 그대로 둘 수 있다.
- 비밀번호: 시연 회원 모두 현재 비밀번호는 `test1234`다. 새 비밀번호는 8~64자, 영문과 숫자를 모두 포함, 현재와 달라야 한다.
- 저장은 목업이라 데이터는 바뀌지 않는다. 기본 정보는 성공 뒤 입력한 값이 칸에 남고, 새로고침하면 원래 값이다.
- 운영자도 같은 화면을 쓴다.
- 오류 문구는 칸 바로 아래, 경고 아이콘과 함께, 글자 크기는 입력과 같은 위치에서 시작한다 (출금 폼과 같은 방식).
- S번호는 S163~S184를 쓴다. 다른 문서·열린 PR의 최대 번호(S162, 당시 크레딧 문서)와 겹치지 않게 다음 번호부터. 크레딧은 11-02 번호 정리로 S348~S381이 됐다.
