# 프론트엔드 출금 요청 관리 (`/admin/withdrawals`)

출금 요청 관리 페이지가 지켜야 하는 요구사항(R)과 시나리오(S)를 모은 문서다. 번호는 다른 문서와 겹치지 않게 R31, S191부터 매긴다. 이 이슈(#42)에서 새로 생긴 시나리오는 `#42-S1`부터 센다. #68에서 새로 생긴 시나리오는 `#68-S11`부터 센다(`#68-S1`~`S10`은 백엔드 [admin-cashout.md](../../backend/payment/admin-cashout.md)가 쓴다). 옛 S번호 동작이 바뀌면 번호는 두고 `(고침 #42: …)`를 붙인다. `[테스트]` 시나리오만 `frontend/e2e/admin-withdrawals.spec.ts`와 1:1이다.

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`만 e2e 테스트와 1:1이고, `[테스트: 파일 번호]`는 그 테스트가 대신 확인한다. `[명령]`은 명령 한 번, `[직접]`은 사람이 화면을 보고 확인한다. (고침 #56)

## 한눈에
- 목적: 운영자가 테스터의 출금 요청(크레딧 현금화)을 확인하고 지급 완료 또는 반려로 처리한다. 요청 금액은 처리 중 잠겨 있고, 지급하면 차감되고 반려하면 회원에게 돌아간다(크레딧 계획 문서 `payment/credits.md` 맥락).
- 스택: 홈과 같다. 실행 방법은 `frontend/README.md`를 본다.
- 화면 구성:
  1. 목록 `/admin/withdrawals`: 운영자 하위 탭(출금 요청이 현재 탭), "처리 대기"·"처리 완료" 탭, 요청 목록
  2. 모달 `?open=<withdrawalKey>`: 회원·금액·받을 계좌(복사 버튼), 처리 양식 또는 처리 결과. 상세 페이지(`/admin/withdrawals/:withdrawalKey`)는 없다. (고침 #42: 상세를 목록 모달로 바꿈)
- 처리 결과는 두 가지다. 테스터 출금 내역의 상태 이름과 맞춘다.
  - 지급 완료: 운영자가 계좌로 송금을 마쳤다. 잠긴 크레딧이 차감된다.
  - 반려: 지급하지 않는다. 사유를 골라야 하고, 사유와 메모는 테스터 출금 내역에 그대로 보인다(고침 #68: 메모는 모든 사유에서 회원에게 보인다). 잠긴 크레딧이 회원에게 돌아간다.
- 디자인: 신고·제재 관리와 같은 토큰과 `components/ui`만 쓴다. 주 버튼은 모달의 "처리하기" 하나다. 결과 배지에는 강조색을 쓰지 않는다. 금액은 `formatWon`("5,000원")으로 적는다. 규칙은 `frontend/DESIGN.md`와 `docs/design-tokens.html`에 있다.
- 데이터: 목업이다(고침 #207: `AUTH_MODE=backend`에서는 서버 값. 아래 "백엔드 연결 (#207)"). 처리 결과는 시연용 쿠키 `demo-admin-withdrawals`에 저장해서 같은 브라우저 안에서만 유지된다. 운영자 홈의 출금 데이터와 같은 출처를 쓴다.
- 결정 필요:
  - 테스터 화면과 연동할지. 같은 브라우저에서 테스터가 신청한 출금(`demo-withdrawals-<role>`)을 운영자 목록에 보여 주고, 처리 결과를 테스터 출금 내역에 반영하는 것. PR #9(`feature/frontend-credits`)가 병합된 뒤 정한다. 그 전까지는 운영자 목업만 쓴다.
  - 반려 사유 목록. 아래 3개로 시작하고 팀에서 확정한다.
  - 최소 출금액, 운영자 처리 기한. 기획 미정이라 화면에 약속하지 않는다.
- 페이지 URL: `docs/page-urls.md`

이 아래 시나리오는 따로 적지 않으면 `demo-role=admin`이다.

## 3. 목록 (R33)
처리 대기는 오래 기다린 순서로, 처리 완료는 최근 처리 순서로 보여 준다. 탭 상태는 URL(`tab`)에 남는다. 계좌번호는 목록에 보여 주지 않는다.

S196 처리 대기 [테스트: admin-withdrawals.spec.ts S207]
- 자동 검사는 처리 대기·처리 완료 목록에 전체 계좌번호가 없음을 지급 완료 흐름에서 함께 확인한다. 아래의 정렬·요약·행 구성은 관련 화면을 바꿀 때 직접 확인한다.
- When  `/admin/withdrawals`에 접속한다
- Then  "처리 대기" 탭에 `aria-current="page"`가 있고 요청 3건이 신청이 오래된 순서다
- Then  목록 위에 "3건 · 25,200원"이 보인다
- Then  각 행에 닉네임, 금액(원), 은행, 경과 시간이 있다
- Then  계좌번호 숫자는 목록 어디에도 없다

S197 예금주 확인 필요 표시 [직접]
- Then  "김민준" 행에 "예금주 확인 필요"가 있다
- Then  다른 두 행에는 없다

S198 처리 완료 [직접]
- When  "처리 완료" 탭을 누른다
- Then  URL에 `tab=done`이 붙고 요청 2건이 최근 처리 순서다
- Then  각 행에 결과("지급 완료" 또는 "반려")와 처리 시각이 있다

S199 없음 [직접]
- Given `demo-data=empty`
- Then  "처리할 출금 요청이 없어요"가 보인다

S200 모달 열기 [직접] (고침 #42: 상세 대신 `?open=`)

- Then  URL이 `/admin/withdrawals?open=withdrawal-1`이고 모달이 열린다

## 4. 모달 (R34)
송금에 필요한 정보는 목록 위 모달에 보여 준다. 모달 상태는 주소(`open`)로 관리하고, 서버가 `searchParams`를 읽어 그린다. 계좌번호 전체는 처리 대기 모달에서만 보여 준다. 계좌 정보는 상세 API(목업 `getWithdrawal`)로 읽는다.

S201 처리 대기 모달 [직접] (고침 #42: 상세 → 모달)
- When  `/admin/withdrawals?open=withdrawal-1`에 접속한다
- Then  닉네임 "이지우", 회원 이름 "이지우", 신청 금액 "5,000원", 신청 시각이 보인다
- Then  받을 계좌 "국민", 계좌번호 "123456789012", 예금주 "이지우"가 보인다
- Then  "계좌번호 복사" 버튼이 있다

S202 예금주가 회원 이름과 다를 때 [직접] (고침 #42: 모달 주소)
- When  `/admin/withdrawals?open=withdrawal-2`에 접속한다
- Then  예금주 "김민지"와 회원 이름 "김민준"이 보이고 "예금주가 회원 이름과 달라요"가 보인다

S203 처리 완료 모달의 계좌 가림 [테스트] (고침 #42: 모달 주소)
- When  `/admin/withdrawals?tab=done&open=withdrawal-4`에 접속한다
- Then  계좌번호는 "****5678"처럼 끝 4자리만 보인다
- Then  "계좌번호 복사" 버튼은 없다

S204 닫기 [직접] (고침 #42: "목록으로" 링크 대신 닫기 버튼)

#42-S2 새로고침 뒤에도 모달 유지 [직접]

#42-S9 Esc로 닫은 뒤 다른 행을 누르면 모달이 다시 열린다 [직접]

- When  Esc로 닫은 뒤 다른 행을 누른다
- Then  주소의 open이 바뀌고 모달이 다시 열린다

## 5. 처리 (R35)
운영자는 결과를 골라 처리하고, 처리한 요청은 처리 대기에서 처리 완료로 옮겨진다. 처리 결과는 다시 바꿀 수 없다. 막히면 페이지를 옮기지 않고 그 자리에서 오류를 보여 준다.

S205 결과를 골라야 처리된다 [직접] (고침 #42: 모달 주소)
- When  결과를 고르지 않고 "처리하기"를 누른다
- Then  처리되지 않고 "처리 결과를 골라 주세요"가 보인다
- Then  주소는 `/admin/withdrawals?open=withdrawal-1` 그대로다

S206 반려는 사유가 있어야 한다 [테스트]
- When  "반려"를 고르고 사유 없이 "처리하기"를 누른다
- Then  처리되지 않고 "반려 사유를 골라 주세요"가 보인다
- When  사유 "기타"를 고르고 메모 없이 "처리하기"를 누른다
- Then  "회원에게 보여 줄 사유를 적어 주세요"가 보인다

S207 지급 완료 [테스트]
- When  `/admin/withdrawals?open=withdrawal-1`에서 "지급 완료"를 고르고 "처리하기"를 누른다
- Then  URL이 `/admin/withdrawals?processed=withdrawal-1`이고 "5,000원을 지급 완료로 처리했어요"가 보인다
- Then  처리 대기가 2건이고 "2건 · 20,200원"이다
- When  "처리 완료" 탭을 누른다
- Then  "이지우" 행이 맨 위에 있고 "지급 완료"가 있다

S208 반려 [직접]
- When  `/admin/withdrawals?open=withdrawal-2`에서 "반려", 사유 "예금주 이름이 회원 정보와 달라요"를 고르고 "처리하기"를 누른다
- Then  "출금 요청을 반려했어요. 잠긴 크레딧이 회원에게 돌아가요"가 보인다
- Then  처리 완료 탭의 "김민준" 행에 "반려"가 있다
- Then  메모를 적지 않았으므로 `/admin/withdrawals?tab=done&open=withdrawal-2` 모달에 "회원에게 보이는 메모"가 없다 (고침 #68)

S209 처리한 요청의 결과 모달 [직접] (고침 #42: 상세 → 모달)
- Given S208을 마친 상태
- When  `/admin/withdrawals?tab=done&open=withdrawal-2`에 접속한다
- Then  처리 양식은 없고 결과 "반려", 사유, 처리 시각이 보인다
- Then  계좌번호는 끝 4자리만 보인다 (S203과 같다)

S210 저장 공간이 모자랄 때 [직접]
- Given 시연용 처리 기록 쿠키가 한도 가까이 차 있다
- When  `/admin/withdrawals?open=withdrawal-1`에서 "반려", 사유 "기타", 메모 80자를 적어 "처리하기"를 누른다
- Then  "시연용 저장 공간이 모자라 처리하지 못했어요"가 보이고 주소는 그대로다
- Then  적은 메모 80자가 입력창에 그대로 있다
- Then  withdrawal-1은 처리 대기에 그대로 있다

S217 막혀도 고른 값이 남는다 [직접]
- When  `/admin/withdrawals?open=withdrawal-1`에서 "반려", 사유 "기타"를 고르고 메모 없이 "처리하기"를 누른다
- Then  "회원에게 보여 줄 사유를 적어 주세요"가 보이고 "반려"와 "기타"가 골라진 채로 있다
- Then  주소는 그대로다 (고른 값과 메모가 주소나 방문 기록에 실리지 않는다)
- When  메모만 적고 "처리하기"를 누른다
- Then  처리된다

S218 반려 메모 안내와 결과 [테스트: admin-withdrawals.spec.ts #68-S11, #68-S12] (고침 #42: 모달) (고침 #68: 모든 반려 메모가 회원에게 보인다)
- 안내 문구와 결과 라벨은 #68-S11, #68-S12가 확인한다.

#68-S11 반려 메모 안내 [테스트]
- When  `/admin/withdrawals?open=withdrawal-1`에 접속해 "반려"를 고른다
- Then  메모 입력창 위에 "메모는 회원에게 그대로 보여요. 사유가 "기타"이면 꼭 적고, 다른 사유는 필요할 때만 적어요."가 보인다 (placeholder가 아니라 입력해도 남는 설명이다)

- 반려 사유는 3개다: "예금주 이름이 회원 정보와 달라요", "계좌번호를 확인할 수 없어요", "기타". "기타"는 메모가 필요하다.
- 반려 메모는 사유와 관계없이 회원에게 그대로 보인다(고침 #68: 전에는 "기타"일 때만 보이는 사유였고 나머지는 운영자 기록이었다). 사유 칸은 늘 고정 문구이고 메모는 "회원에게 보이는 메모"로 따로 보여 준다. 메모는 "기타"만 필수이고 나머지는 선택이다. 지급 완료에는 메모를 받지 않는다. 운영자 전용 메모 칸은 없다.
- 처리 양식은 `useActionState`로 제출한다. 막히면 Server Action이 오류만 돌려주고 페이지를 옮기지 않아서, 고른 값과 메모가 화면에 그대로 남는다(S210, S217). React가 폼 액션 뒤 입력을 자동으로 비우지 않도록 `onSubmit`에서 직접 제출한다. 처리되면 Server Action이 목록으로 보낸다.
- 반려 메모는 80자까지다. 신고 처리 메모와 같은 이유(쿠키 4096바이트 한도, 한글 9바이트 인코딩)로 저장 전에 인코딩한 길이를 확인하고, 넘으면 처리하지 않고 알린다(S210).
- 처리 결과는 쿠키 `demo-admin-withdrawals`에 요청 키·결과·사유·메모·처리 시각으로 저장한다. 테스터 쪽 쿠키 `demo-withdrawals-<role>`과 이름이 겹치지 않게 한다(`demo-withdrawals-admin`은 운영자 본인의 신청 기록 자리다). 실제 API를 붙이면 이 쿠키를 쓰지 않는다.
- "지급 완료"는 운영자가 서비스 밖에서 송금을 마쳤다는 기록이다. 실제 송금·계좌 실명 확인은 하지 않는다.
- 처리 결과는 다시 바꿀 수 없다. 송금 실패 뒤 되돌리기는 미정이다.
- 처리를 마치면 목록으로 돌아가 결과 문구를 한 번 보여 준다(`?processed=<요청 키>`). 문구는 주소의 값이 아니라 그 요청의 처리 기록과 금액 데이터로 만든다. 처리되지 않은 요청이면 문구를 보이지 않는다(S219). 실제 API를 붙여도 금액은 서버 데이터에서 가져온다.
- 처리 완료 뒤에는 계좌번호를 끝 4자리만 보여 준다. 송금이 끝난 뒤에는 전체 번호가 필요 없다.
- 금액은 "원"으로 적는다. 1크레딧 = 1원이고, 운영자에게는 송금할 금액이 중요하다.
- 모달은 `?open=<요청 키>`로 연다. 없는 키는 모달 없이 목록만 보여 준다. 상태 탭 링크는 open을 넣지 않는다(#42-S1). 목록에서 모달을 열 때는 `replace`로 기록을 쌓지 않는다. 처리 뒤에는 지금처럼 `?processed=<key>`로 목록에 결과 문구를 보여 준다.

## 백엔드 연결 (#207)
`AUTH_MODE=backend`에서 `/admin/withdrawals`의 목록·모달·처리가 서버 운영자 API를 쓴다. API는 [admin-cashout.md](../../backend/payment/admin-cashout.md)(`GET /api/v1/admin/withdrawals?tab=pending|done`, `GET /api/v1/admin/withdrawals/{id}`, `PUT /api/v1/admin/withdrawals/{id}`)다. 값이 없으면 지금처럼 목업(시연용 쿠키)이다. 번호는 `#207-S1`부터다. 회원 쪽 신청·내역은 [credits.md](../payment/credits.md)의 `#206`이다.

정한 것 (#207)
- **요청 키는 서버의 요청 id(숫자)다.** 목업의 키 목록에 있는지 보던 확인을 백엔드 모드에서는 서버 id가 될 수 있는 숫자인지 확인으로 바꾼다. 0으로 시작하지 않는 18자리 이하 숫자만 받는다. 더 긴 숫자는 서버 id(Long)를 넘을 수 있고, 그러면 서버가 404가 아니라 400으로 답해 오류 화면이 되므로 서버에 묻지 않는다. 없는 id는 서버가 404로 답하고, 둘 다 모달 없이 목록만 보인다.
- **목록의 순서는 서버가 정한다.** 처리 대기는 신청이 오래된 순, 처리 완료는 최근 처리 순이다. 화면은 다시 정렬하지 않는다.
- **계좌는 서버가 준 대로 보인다.** 처리 대기는 계좌번호·예금주 전체, 처리 완료는 서버가 가려서 준다(끝 4자리, 이름 가운데 가림). "예금주 확인 필요"는 처리 대기 요청에서만 가입 실명과 비교한다(끝난 요청의 예금주는 가려져 와서 비교하지 않는다).
- **처리는 `PUT`으로 보낸다.** 지급은 `decision=PAID`만, 반려는 `decision=REJECTED`와 사유(`HOLDER`/`ACCOUNT`/`OTHER`), 메모를 보낸다. 사유 필수, 기타면 메모 필수, 메모 80자는 화면에서 먼저 막고 서버도 같은 규칙으로 다시 본다. 서버가 처리하면 지급은 회원의 잠긴 금액이 줄고 내역에 "출금 지급"이 남고, 반려는 잠긴 금액이 적립으로 돌아간다.
- **이미 처리한 요청은 서버가 막는다(409).** 다른 운영자가 먼저 처리했으면 그 결과를 모달로 새로 보여 준다(목업과 같은 동작). 그 밖의 서버 실패는 처리 폼 안에 "서버가 처리하지 못했어요. 잠시 후 다시 시도해 주세요."로 보이고 고른 값은 그대로 남는다.
- **처리하면 회원 화면도 새 값을 읽게 한다.** `revalidatePath("/my", "layout")`.
- **서버에 닿지 못하거나 목록을 읽지 못하면 오류로 멈춘다**(목업으로 채우지 않는다). 운영자가 아니면 지금처럼 접근 거부 안내다.
- 운영자 홈(`/admin`)의 "처리 대기 출금" 요약·가장 오래 기다린 요청·최근 요청도 같은 함수를 읽어 서버 값이다. 세 곳이 한 요청 안에서 대기 목록을 한 번만 읽는다(대기 응답에는 계좌번호·예금주 전체가 들어 있다). 출금 API만 실패하면 홈은 열리고 출금 카드·최근 요청의 출금 칸이 "불러오지 못했어요"로 보이고 "오래 기다린 요청" 목록 아래에 "출금 요청은 불러오지 못했어요."가 보이며(신고만 있는 목록이 완전한 목록처럼 보이지 않게), 신고 집계와 목록은 그대로다.
- 목업 모드의 동작과 화면은 바꾸지 않는다.

확인 데이터 (#207)

- 처리 대기 요청은 회원이 `/my/credits/withdrawals`에서 신청해서 만든다(#206). 처리 완료 목록은 그 요청을 이 화면에서 지급·반려해서 만든다. 계좌를 바꿔 여러 번 신청하면 은행·예금주가 다른 요청을 볼 수 있다.

#207-S1 처리 대기·처리 완료 목록을 서버 값으로 본다 [직접]
- Given 처리 중·지급 완료·반려 요청이 있다, `/admin/withdrawals`
- Then  "처리 대기"에는 처리 중인 요청이 신청이 오래된 순으로, "처리 완료"에는 지급 완료·반려 요청이 최근 처리 순으로 보인다. 처리 완료 행에는 "지급 완료"·"반려" 배지가 있다

#207-S2 상세에서 계좌가 처리 상태에 맞게 보인다 [직접]
- When  처리 대기 요청을 연다
- Then  은행·계좌번호 전체·예금주 전체가 보이고 복사 버튼이 있다. 예금주가 가입 실명과 다르면 "예금주 확인 필요"가 보인다
- When  처리 완료 요청을 연다
- Then  계좌번호는 끝 4자리만, 예금주는 가려진 이름이 보이고 복사 버튼과 "예금주 확인 필요"는 없다

#207-S3 지급 완료로 처리하면 회원의 잠긴 금액이 빠진다 [직접]
- Given 회원이 5,000을 신청한 요청(회원의 출금 처리 중 5,000)
- When  운영자가 "지급 완료"로 처리한다
- Then  목록으로 돌아와 처리 결과 문구가 보이고 요청이 "처리 완료"로 옮겨진다
- Then  회원의 `/my/credits`에서 "출금 처리 중"이 5,000 줄고 총 잔액·헤더가 5,000 줄며, 크레딧 내역에 "출금 지급 −5,000"이 남는다. 회원의 출금 내역에는 "지급 완료"로 보인다

#207-S4 반려하면 사유가 남고 잠긴 금액이 적립으로 돌아간다 [직접]
- Given 회원이 5,000을 신청한 요청
- When  사유 "예금주 불일치"를 골라 반려한다
- Then  회원의 "출금 처리 중"이 5,000 줄고 "적립 크레딧"이 5,000 늘며 총 잔액은 그대로다. 크레딧 내역에는 새 줄이 없다. 회원 출금 내역에 "반려"와 사유 문구가 보인다
- When  사유 "기타"를 고르고 메모 없이 반려한다
- Then  "…에게 보여 줄 사유를 적어 주세요."가 보이고 요청은 처리되지 않는다. 메모를 적으면 처리되고 회원 출금 내역에 사유 옆에 메모가 보인다

#207-S5 이미 처리한 요청은 다시 처리되지 않는다 [직접]
- Given 같은 처리 대기 요청을 두 창에서 열어 둔다
- When  첫 창에서 지급 완료로 처리한 뒤 둘째 창에서 "반려"로 처리한다
- Then  둘째 창은 처리되지 않고 이미 처리된 결과(지급 완료)가 모달로 보인다. 회원의 잔액은 한 번만 바뀐다

#207-S6 운영자가 아니면 접근할 수 없다 [직접]
- Given 일반 회원, 비로그인
- Then  일반 회원은 접근 거부 안내, 비로그인은 로그인으로 간다

#207-S7 서버 응답을 운영자 화면 값으로 바꾼다 [테스트: credit-balance.test.ts #207-S7]
- Given 서버 운영자 출금 응답(처리 대기·지급 완료·반려, 사유·메모, 오프셋 시각)
- Then  처리 대기는 처리 결과가 없고, 지급 완료는 "지급", 반려는 사유 키와 메모를 갖는다. 회원 이름·계좌·신청 시각이 그대로 옮겨진다. 사유가 없는 반려도 오류 없이 변환된다

#207-S8 서버가 처리하지 못하면 폼 안에 이유가 보인다 [직접]
- Given 처리 요청이 서버에서 실패한다(예: 서버 오류)
- When  처리하기를 누른다
- Then  폼 안에 "서버가 처리하지 못했어요. 잠시 후 다시 시도해 주세요."가 보이고 고른 값과 메모가 그대로 남는다. 요청은 처리 대기에 남는다

#207-S9 목업 모드는 그대로다 [테스트: admin-withdrawals.spec.ts]
- Given `AUTH_MODE`가 `backend`가 아니다
- Then  기존 `admin-withdrawals.spec.ts`가 그대로 통과한다

#207-S10 서버 id가 될 수 없는 키는 없는 요청으로 본다 [테스트: credit-balance.test.ts #207-S10]
- Given `/admin/withdrawals?open=<키>`의 키가 `abc`, `0`, `007`, 19자리 이상 숫자(예: `99999999999999999999`)다
- Then  서버에 묻지 않고 모달 없이 목록만 보인다(오류 화면이 아니다). `1`, 18자리 숫자는 서버에 묻는다

#207-S11 운영자 홈은 출금 대기 목록을 한 번만 읽고, 출금 API만 실패해도 열린다 [직접]
- Given 처리 대기 출금 요청이 있다, `/admin`
- Then  "출금 요청 1건 · 요청 금액 …", "오래 기다린 요청"의 출금 줄, "최근 요청"의 출금 칸이 서버 값으로 보이고, 한 번 열 때 서버의 출금 대기 목록 조회는 한 번이다
- Given 출금 대기 목록 API만 실패한다(예: 500)
- Then  운영자 홈이 오류 없이 열리고 신고 집계·오래 기다린 신고·최근 신고는 그대로다. 출금 카드에는 "불러오지 못했어요", 최근 요청의 출금 칸에는 "불러오지 못했어요."가 보이고 "0건"이라고 하지 않는다. "오래 기다린 요청" 목록 아래에는 "출금 요청은 불러오지 못했어요."가 보이고, 목록이 비어 있어도 "기다리는 요청이 없어요"가 아니라 "기다리는 신고가 없어요."로 보인다
