# 프론트엔드 회원 관리 (`/admin/users`)

회원 관리 페이지가 지켜야 하는 요구사항(R)과 시나리오(S)를 모은 문서다. 번호는 다른 문서와 겹치지 않게 R39, S220부터 매긴다(열린 PR #12 출금 요청 관리가 R38, S219까지 쓴다). 테스터·개발자 겸업 활동 시나리오(옛 임시 번호 S531)는 11-03에 S527로 확정했다. S번호는 `frontend/e2e/admin-users.spec.ts`의 테스트 이름과 1:1로 맞춘다. 테스트를 추가하거나 바꾸면 이 문서도 함께 고친다.

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`만 e2e 테스트와 1:1이고, `[테스트: 파일 번호]`는 그 테스트가 대신 확인한다. `[명령]`은 명령 한 번, `[직접]`은 사람이 화면을 보고 확인한다. (고침 #56)

## 한눈에
- 목적: 운영자가 회원을 찾아 기본 정보와 제재 이력, 받은 신고를 한 화면에서 확인한다. 신고·제재 관리 문서가 "제재 이력 화면, 회원별 제재 조회"를 이 페이지로 미뤄 두었다(`admin/reports.md` 범위 밖).
- 스택: 홈과 같다. 실행 방법은 `frontend/README.md`를 본다.
- 화면 구성:
  1. 목록 `/admin/users`: 운영자 하위 탭(회원이 현재 탭), 닉네임 검색, "전체"·"제재 이력 있음"·"검토 대기 신고 있음" 필터, 회원 목록
  2. 상세 `/admin/users/:userKey`: 기본 정보, 활동 요약(테스터 활동·개발자 활동), 제재 이력, 받은 신고
- 이번 범위는 **조회**다(제재 1단계: 이력 보기). 제재 이력은 신고·제재 관리에서 "인정"한 신고로 만든다. 제재 단계가 정해지면 나눠서 더한다.
  - 신고에서 시작하는 제재: 신고·제재 관리에서 인정하면서 처리한다.
  - 현재 상태 표시(2단계)와 신고 없이 하는 직접 제재·해제(3단계): 회원 상세에 더한다. README의 "악의적인 미완료 반복"은 신고가 아니라서 회원 상세의 미완료 횟수를 보고 판단하기 때문이다.
- 디자인: 신고·제재 관리와 같은 토큰과 `components/ui`만 쓴다. 이 페이지에는 주 버튼이 없다. 제재 이력 배지에는 강조색을 쓰지 않는다. 규칙은 `frontend/DESIGN.md`와 `docs/design-tokens.html`에 있다.
- 데이터: 목업이다. 제재 이력과 받은 신고는 신고 목업과 시연용 쿠키 `demo-reports`에서 계산한다. 그래서 신고·제재 관리에서 신고를 처리하면 회원 관리에도 바로 반영된다. 새 쿠키는 만들지 않는다.
- 개인정보: 실명과 이메일은 목록에 보여 주지 않고, 상세에서도 일부를 가려서 보여 준다. 회원 관리는 조회 화면이라 전체 정보가 필요하지 않다. 송금처럼 목적이 있는 화면(출금 요청 처리)에서만 필요한 정보를 전부 보여 준다.
- 결정 필요: 제재 단계와 각 단계의 효과. 예: 인정 1회 경고, 2회 7일 동안 테스트 지원 정지, 3회 영구 정지. 정해지면 위 2·3단계를 더한다.
- 페이지 URL: `docs/page-urls.md`

이 아래 시나리오는 따로 적지 않으면 `demo-role=admin`이다.

## 1. 테마 (R39)
신고·제재 관리와 같은 토큰을 쓴다. 이 페이지는 처리하는 화면이 아니라서 강조색 바탕 버튼이 없다.

S220 배지 [직접]
- Given `prefers-color-scheme: light` (`dark`도 같다)
- When  `/admin/users?filter=sanctioned`에 접속한다
- Then  "제재 이력 1건" 배지의 글씨색이 `--accent`가 아니다

S221 주 버튼 없음 [직접]
- When  `/admin/users`와 `/admin/users/user-4`에 접속한다
- Then  본문에 강조색 바탕의 버튼이나 링크가 없다

목록과 상세 모두 운영자에게만 보인다. 규칙은 운영자 홈 R15와 같다.

## 3. 목록 (R41)
회원을 최근 가입 순서로 보여 준다. 실명과 이메일은 목록에 보여 주지 않는다.

S225 전체 [테스트]
- When  `/admin/users`에 접속한다
- Then  "전체" 필터에 `aria-current="page"`가 있고 회원 10명이 최근 가입 순서다
- Then  각 행에 닉네임과 가입일이 있고, 역할(테스터·개발자)은 없다. 한 사람이 둘 다 할 수 있기 때문이다
- Then  실명·이메일은 목록 어디에도 없다

S226 제재·신고 표시 [직접]
- Then  "서준호" 행에 "제재 이력 1건"이 있다
- Then  "오태민", "윤소희", "강민서" 행에 "검토 대기 신고 1건"이 있다
- Then  다른 행에는 두 표시가 없다

S227 상세로 이동 [직접]
- When  "서준호" 행을 누른다
- Then  URL이 `/admin/users/user-4`이다

S228 없음 [직접]

- Then  "회원이 없어요"가 보인다

## 4. 검색과 필터 (R42)
닉네임 일부로 찾고, 필터로 확인이 필요한 회원만 본다. 검색어와 필터는 URL(`q`, `filter`)에 남고 함께 쓸 수 있다.

S229 검색 [테스트]
- When  검색창 "닉네임 검색"에 `민`을 넣고 제출한다
- Then  URL에 `q=%EB%AF%BC`가 붙고 "강민서", "김민준", "오태민" 3명만 보인다

S230 검색 결과 없음 [직접]
- When  `/admin/users?q=없는회원`에 접속한다
- Then  "'없는회원'에 맞는 회원이 없어요"가 보이고 검색창에 `없는회원`이 남아 있다

S231 제재 이력 있음 [테스트]
- When  "제재 이력 있음"을 누른다
- Then  URL이 `/admin/users?filter=sanctioned`이고 "서준호" 1명만 보인다

S232 검토 대기 신고 있음 [직접]
- When  "검토 대기 신고 있음"을 누른다
- Then  URL이 `/admin/users?filter=reported`이고 "강민서", "윤소희", "오태민" 3명이 보인다

S233 검색과 필터를 함께 [테스트]
- When  `/admin/users?filter=reported&q=민`에 접속한다
- Then  "강민서", "오태민" 2명만 보인다
- When  "전체"를 누른다
- Then  URL이 `/admin/users?q=%EB%AF%BC`이고 3명이 보인다 (검색어는 남는다)

S234 알 수 없는 필터 [직접]
- When  `/admin/users?filter=foo`에 접속한다
- Then  "전체" 필터가 선택되고 10명이 보인다

S249 검색과 필터를 함께 써서 결과가 없을 때 [직접]
- When  `/admin/users?filter=sanctioned&q=민`에 접속한다
- Then  "'민' 검색과 '제재 이력 있음' 필터에 함께 맞는 회원이 없어요"가 보인다 (원인이 필터일 수도 있어서 둘 다 말한다)
- 참고: 검색어만 있으면 "'민'에 맞는 회원이 없어요", 필터만 있으면 "'제재 이력 있음'에 맞는 회원이 없어요"다.

S280 뒤로 가기 [테스트]
- When  검색창에 `민`을 넣고 제출한 뒤, `준`을 넣고 제출한다
- Then  "김민준", "서준호" 2명이 보인다
- When  브라우저에서 뒤로 간다
- Then  URL이 `/admin/users?q=%EB%AF%BC`이고 3명이 보이며, 검색창에도 `민`이 있다 (주소·목록·검색창이 어긋나지 않는다)
- 참고(10-31): `next/form`은 같은 페이지로 이동할 때 입력칸을 그대로 두어 `defaultValue`가 다시 적용되지 않는다. 입력칸에 `key={query}`를 달아 주소의 검색어가 바뀌면 새로 그린다.

## 5. 상세 (R43)
판단에 필요한 정보를 한 화면에 모은다. 실명과 이메일은 상세에서만, 그것도 일부를 가려서 보여 준다.

S237 개발자만 한 회원 [직접]

- Then  "활동" 영역에 테스터 활동(참여 확정 4회 등)과 개발자 활동(프로젝트 2개, 모집 건 3개, 구독 중)이 함께 보이고 "활동이 없어요"는 없다

S238 제재 이력 [테스트]

- Then  "제재 이력" 영역에 "제재 이력이 없어요"가 보인다

S240 기각된 신고 [테스트]

## 6. 신고·제재 관리와 연결 (R44)
제재 이력은 신고 처리 결과에서 계산하므로, 신고를 처리하면 회원 관리에 바로 반영된다.

S242 인정하면 제재 이력이 생긴다 [테스트]
- When  `/admin/reports/report-4`(대상 "강민서")에서 "인정"으로 처리한다
- When  `/admin/users/user-10`에 접속한다
- Then  "제재 이력"에 "채팅에서 부적절한 표현을 썼어요" 1건이 있고, "받은 신고"의 그 신고는 "인정"이다
- When  `/admin/users?filter=sanctioned`에 접속한다
- Then  "서준호", "강민서" 2명이 보인다

S243 기각하면 제재 이력은 그대로다 [직접]
- When  `/admin/reports/report-1`(대상 "오태민")에서 "기각"으로 처리한다
- When  `/admin/users/user-6`에 접속한다
- Then  "받은 신고"의 그 신고는 "기각"이고 "제재 이력이 없어요"가 보인다
- Then  목록 "검토 대기 신고 있음" 필터에 "오태민"은 없다

S244 신고 상세에서 회원으로 [직접]
- When  `/admin/reports/report-1`에 접속한다
- Then  "대상 테스터" 값 "오태민"이 `/admin/users/user-6`으로 가는 링크다
- When  `/admin/reports/report-4`에 접속한다
- Then  "대상 회원" 값 "강민서"가 `/admin/users/user-10`로 가는 링크다

## 7. 로딩과 접근성 (R45)
제목·검색창·필터는 목록 데이터를 기다리지 않고, 검색은 키보드로 쓸 수 있으며, 좁은 화면에서 가로로 넘치지 않는다.

S245 로딩 [직접]
- Given `demo-data=slow` (1.5초 지연)
- When  `/admin/users`에 접속한다 (응답 시작 직후)
- Then  운영자 하위 탭, 검색창, 필터가 보이고 목록 스켈레톤이 보인다
- Then  응답 뒤 스켈레톤이 없다

S246 검색 양식 [직접]
- Then  검색창은 이름이 "닉네임 검색"인 `searchbox`이고, Enter로 제출된다
- Then  필터 묶음은 이름이 "회원 필터"인 `navigation`이다

S247 좁은 화면 [테스트: pages.spec.ts #56-S1]
- Given 너비 375px
- When  `/admin/users`와 `/admin/users/user-4`에 접속한다
- Then  페이지에 가로 스크롤이 없다 (하위 탭·필터 줄 안의 스크롤만 예외)

## 8. 구조 (R46)
권한은 페이지와 데이터 함수에서 각각 확인한다. 이 페이지에는 Server Action이 없다. 검색은 GET 양식이라 `"use client"`를 늘리지 않는다. 회원 상세는 `params`를 Suspense 안에서 읽는다(이유는 `admin/reports.md` R30).

S248 [명령]
- When  `grep -L "requireAdmin" src/app/admin/users/page.tsx src/app/admin/users/*/page.tsx`
- Then  결과가 없다
- When  `grep -rl '"use client"' src/app/admin src/features/admin`
- Then  운영자 폴더의 목록이 `admin/reports.md` S445과 같다 (회원 관리는 더하지 않는다)

## 데모 데이터와 가정
- 회원 목업은 신고·출금 목업에 나오는 10명이다. 키는 신고(`report-1`)·출금(`withdrawal-1`) 목업처럼 `user-<번호>`이고, 가입이 오래된 회원부터 번호를 붙인다. 주소에는 아이디나 이름을 쓰지 않는다. 아이디는 회원이 바꿀 수 있어 링크가 깨지고, 이름·아이디는 개인정보라 방문 기록과 로그에 남기지 않는다.

  표의 "활동 기록"은 역할이 아니라 그 회원이 해 본 활동을 요약한 값이다. 목록에는 나오지 않고 상세의 "활동"에서 본다. 출금 요청의 신청자는 테스트로 크레딧을 받은 회원이어야 해서 테스터 활동이 있는 회원으로 맞췄다.

  | 키 | 닉네임 | 활동 기록 | 가입 | 받은 신고 |
  | --- | --- | --- | --- | --- |

- 신고 목업의 대상은 닉네임만 있어서, 신고에 대상 회원 키(`targetUserKey`)를 더해 연결한다. 모집 글 신고(report-3)는 대상 회원이 없다.
- 제재 이력 = 그 회원이 대상인 신고 중 "인정"된 것. 받은 신고 = 그 회원이 대상인 모든 신고. 둘 다 신고 목업과 `demo-reports` 쿠키를 합친 결과로 계산한다.
- 목록과 상세 제목에 보이는 이름은 **닉네임**이다. 시연용 목업은 신고·출금 목업이 처음부터 사람을 실명처럼 생긴 닉네임("서준호")으로 적어 두어서, 회원 관리도 같은 값을 쓴다. 그래서 목록이 실명을 보여 주는 것처럼 보일 수 있다.
- 실명도 닉네임과 같다고 둔다(시연용). 그래서 상세에 닉네임 "서준호"와 실명 "서*호"가 나란히 보인다. 실제 데이터에서는 둘이 다르다.
- 목업끼리도 맞지 않는 곳이 있다. 마이페이지 목업은 실명 "한서윤"의 닉네임이 "윤슬"이다. 페이지마다 목업을 따로 만들고 있어서, 시연용 회원 이름(닉네임·실명)은 나중에 팀에서 한 번에 정해 모든 목업을 맞춘다.
- 가리는 규칙:
  - 실명: 두 글자는 뒤 글자를(`김*`), 세 글자 이상은 처음과 끝 글자만 남기고 가운데를 `*`로 가린다(`서*호`, `남**수`).
  - 이메일: `@` 앞의 앞 두 글자만 남기고 `***`로 가린다(`me***@example.com`). 도메인은 그대로 둔다.
  - 이메일은 이름과 관계없는 `member<두 자리 번호>@example.com`이다(user-4 → `member04@example.com`).
- 한 사람이 테스터도 개발자도 될 수 있어서(백엔드 Role은 USER·ADMIN뿐이다) 목록에는 역할을 쓰지 않고, 상세의 "활동"에 테스터 활동과 개발자 활동을 둘 다 보여 준다. 해 본 적이 없는 쪽은 "…활동이 없어요"로 적는다. 시연용으로 user-2(정하린)만 둘 다 한다.
- 활동 요약 수치는 시연용 고정값이다. 테스터는 참여 확정·피드백 제출·미완료, 개발자는 프로젝트·모집 건·구독 여부다. 미완료는 README의 "악의적인 미완료 반복"을 판단할 때 보는 값이다.
- 운영자 계정은 목록에 넣지 않는다.
- 검색은 닉네임 부분 일치이고, 앞뒤 공백은 무시한다. 최대 20자까지 받는다.
- 목록 정렬은 최근 가입 순서 하나다.

## 범위 밖
- 현재 제재 상태 표시, 신고 없이 하는 직접 제재(경고·참여 정지·탈퇴 처리)와 제재 해제. 제재 단계가 정해지면 회원 상세에 더한다. 신고로 시작하는 제재는 신고·제재 관리에서 인정하면서 처리한다.
- 제재 효과(정지된 테스터의 지원 막기 등). 모집·지원 화면도 함께 바꿔야 한다.
- 실명·이메일 "전체 보기"와 열람 기록(누가 언제 어떤 회원의 정보를 봤는지), 운영자 권한 나누기. 실제 로그인과 API를 붙일 때 더한다. 개인정보보호법의 안전성 확보조치 기준(접근 권한 최소화, 접속 기록 보관)을 그때 확인한다.
- 회원별 출금 이력 (출금 요청 관리 PR #12가 병합된 뒤 더한다)
- 회원 정보 수정, 역할 변경, 운영자 계정 관리
- 정렬 바꾸기, 페이지 나누기, 가입 기간 필터
- 회원 지표(가입 수 추이 등). 통계 대시보드는 기능 후보 4순위다.
- 실제 권한 검사(서버 API 인가)와 저장
