# 버전 비교 짝 지키기와 N:M 짝 (#284)

버전 별 분석 탭의 짝(직전 버전 그룹 → 이번 버전 그룹)을 그룹 코드 대신 연결 테이블로 저장해, 한 그룹이 여러 그룹과 이어지게 하고(N:M), 개발자가 고친 짝은 다시 비교해도 지킨다. 다시 분석·비교하기 전에 확인 창을 띄운다. 비교 실행·조회는 [AI 버전 간 비교(#108)](ai-version-comparison.md), 짝 저장 API는 [버전 별 분석 탭 API(#168)](version-tab-api.md)를 고친다. 시나리오는 `#284-S1`부터 센다.

## 한눈에
- 끝나면: 직전 그룹 하나가 이번 그룹 여러 개로 나뉘거나 여러 직전 그룹이 이번 그룹 하나로 합쳐진 것을 잇고 고칠 수 있다. 고친 짝은 다시 비교해도 남는다
- 결정 필요: 없음
- 규모: 4단계(분석 서버, 백엔드, 화면, 기존 데이터)

## 정한 것 (11-22)

| # | 결정 | 이유 |
| --- | --- | --- |
| 1 | 짝은 `group_links`(이번 그룹 `current_group_id`, 직전 그룹 `previous_group_id`) 한 행으로 저장한다. 같은 쌍은 한 번만(유니크 제약) | 그룹 하나가 코드 하나만 가져 1:1만 나타낼 수 있었다. #283으로 그룹이 넓어져 여러 직전 그룹이 이번 그룹 하나로 합쳐지는 경우가 잦다 |
| 2 | 그룹 코드는 분석할 때 받은 값 그대로 두고, 비교와 짝 저장이 바꾸지 않는다. 이어짐·새로 생김·보고 안 됨은 연결로 계산한다: 연결이 있는 이번 그룹은 "이전에도 있음", 없으면 "신규", 어느 연결에도 없는 직전 그룹은 "이번 버전에서 보고되지 않음" | 짝이 코드에서 연결로 옮겨 가 코드를 이어받을 이유가 없다. 코드는 화면에 보이지 않는다 |
| 3 | 개발자가 짝을 고친 이번 그룹은 `cluster_groups.links_edited_at`에 시각을 남긴다. 다시 비교할 때 이 그룹의 짝(풀어 둔 빈 짝 포함)은 그대로 두고, 나머지 이번 그룹의 연결만 지우고 AI 응답으로 다시 만든다 | 사람이 맞춘 결과를 지킨다(이슈 #284 결정). 빈 짝도 "짝 없음"으로 고친 것이라 지킨다 |
| 4 | 다시 비교할 때 고친 그룹의 짝을 분석 서버에 `fixedPreviousGroupIds`로 보낸다. 분석 서버는 그 그룹의 짝을 그대로 결과에 넣고 AI가 그 그룹에 낸 짝은 버리며, 프롬프트에 고정된 짝을 보여 요약에 반영한다. 고치지 않은 그룹과 직전 그룹은 null이다 | 요약이 고친 짝과 어긋나지 않게 한다. 백엔드도 저장할 때 고친 그룹의 연결을 바꾸지 않아 두 번 지킨다 |
| 5 | AI 짝은 N:M을 허용하고, 같은 쌍이 두 번 오면 한 번만 저장한다. 다른 버전의 그룹이나 없는 id는 지금처럼 버린다 | 분석 서버는 이미 1:N을 허용했지만 백엔드가 버렸다 |
| 6 | 짝 저장은 이번 그룹마다 직전 그룹 목록(`previousGroupIds`)을 받는다. 빈 목록은 짝 없음이다. 보낸 그룹의 연결을 그 목록으로 바꾸고 `links_edited_at`을 남긴다. 이번 버전 그룹이 아닌 `groupId`, 직전 버전 그룹이 아닌 id, 같은 `groupId` 두 번, 한 목록 안의 같은 id 두 번은 400 `INVALID_INPUT`이다. 같은 직전 그룹을 여러 이번 그룹에 이어도 된다 | #168 결정 5처럼 사람이 고른 값은 조용히 버리지 않는다 |
| 7 | 비교 응답의 `groups[]`에 `previousGroupIds`(이어진 직전 그룹 id)를 더한다. `previouslyReported`는 그대로 둔다(목록이 비어 있지 않으면 true) | 화면이 코드를 맞대지 않고 응답의 연결로 짝을 그린다 |
| 8 | 다시 분석하면 지우는 그룹(GitHub에 등록하지 않은 그룹)의 연결도 양쪽 모두 지운다. GitHub에 등록해 남는 그룹은 연결과 `links_edited_at`을 그대로 둔다 | 지운 그룹을 가리키는 연결이 남으면 외래 키에 걸려 저장이 실패한다 |
| 9 | 화면은 결과가 있을 때 "AI 비교 분석 갱신하기"와 "AI 분석 갱신하기"를 누르면 확인 창을 띄운다. 처음 실행할 때는 띄우지 않는다 | 비교 갱신은 고치지 않은 짝과 요약이 바뀌고, 분석 갱신은 그 버전 그룹이 새로 만들어져 고친 짝·이름·이슈 초안이 사라진다 |
| 10 | 이미 저장된 비교의 짝은 `backend/scripts/add_group_links.sql`로 한 번 옮긴다: 비교한 두 버전에서 코드가 같은 그룹 쌍을 연결로 넣는다 | Flyway가 없다. 옮기지 않으면 배포 뒤 모든 비교가 "짝 없음"으로 보인다 |

## API

### 비교 조회·실행 응답 (고침 #284: 연결을 더함)
```json
{ "groups": [ { "groupId": 21, "groupCode": "3", "name": "로그인", "category": "BUG", "improvementRank": 1, "previouslyReported": true, "previousGroupIds": [11, 12] } ],
  "notReportedGroups": [] }
```

### 짝 저장 `PUT .../{recruitmentId}/version-comparison/links` (고침 #284: 직전 그룹을 여러 개 받음)
```json
{ "links": [ { "groupId": 21, "previousGroupIds": [11, 12] }, { "groupId": 23, "previousGroupIds": [] } ] }
```

### 분석 서버 `POST /v1/comparisons`
- 이번 버전 그룹에 `fixedPreviousGroupIds`(고친 그룹만, 빈 목록 가능)를 더한다. 없거나 null이면 AI가 짝짓는다
- 응답 `matches`에는 고정한 짝도 들어 있다. 이번 그룹 하나가 여러 직전 그룹과 이어질 수 있다

## 1. N:M 짝 (#284-R1)

#284-S1 AI가 N:M으로 잇기 [테스트] (고침 #108-S1: 코드를 이어받지 않고 연결로 저장)
- Given 1버전 g11·g12, 2버전 g21·g22·g23
- When  분석 서버가 g21←g11, g21←g12, g23←g11을 준다
- Then  세 연결이 저장되고, 응답에서 g21의 `previousGroupIds`는 [g11, g12], g23은 [g11], g22는 빈 목록·"신규"다. 보고 안 된 그룹은 없다. 그룹 코드는 바뀌지 않는다

#284-S2 잘못된 AI 짝 [테스트] (고침 #108-S3: 이미 짝지은 그룹도 받음)
- When  응답에 다른 버전의 그룹, 없는 id, 같은 쌍 두 번이 섞여 있다
- Then  잘못된 짝은 버리고 같은 쌍은 한 번만 저장한다

#284-S3 짝 고치기 [테스트] (고침 #168-S5·S6: 코드 대신 연결을 바꿈)
- When  g23을 [g11, g12]와 잇고 g21의 짝을 푼다([])
- Then  g23은 두 직전 그룹과, g21은 짝 없이 저장되고 두 그룹에 `links_edited_at`이 남는다. 요약과 비교 시각은 그대로다. 보내지 않은 g22의 연결은 그대로다

#284-S4 잘못된 짝 [테스트] (고침 #168-S7: 같은 직전 그룹을 여러 이번 그룹에 이어도 됨)
- When  직전 버전 그룹을 `groupId`에, 이번 버전 그룹을 `previousGroupIds`에 넣거나, 한 목록에 같은 id를 두 번 넣는다
- Then  400 `INVALID_INPUT`이고 연결은 하나도 바뀌지 않는다

## 2. 고친 짝 지키기 (#284-R2)

#284-S5 다시 비교 [테스트]
- Given g21의 짝을 풀고 g23을 g11과 이어 저장했다
- When  다시 비교하고 분석 서버가 g21←g11, g22←g12를 준다
- Then  분석 서버에 g21은 `fixedPreviousGroupIds` [], g23은 [g11], g22는 null로 간다
- Then  g21은 짝 없음, g23은 g11 그대로이고 g22만 g12와 이어진다. 요약은 새로 저장된다

#284-S6 분석 서버의 고정 짝 [테스트: analysis-server test_domain.py, test_api.py]
- Given 이번 그룹 하나가 고정 짝을 가진다
- When  AI가 그 그룹에 다른 짝을 낸다
- Then  결과에는 고정 짝만 있고, 프롬프트에 고정 짝이 표시된다

#284-S7 다시 분석하면 지운 그룹의 연결도 지움 [테스트]
- Given 2버전 그룹이 1버전 그룹과 이어져 있고, 2버전 그룹 하나는 GitHub에 등록했다
- When  2버전을 다시 분석한다
- Then  지운 그룹의 연결은 없어지고, 등록한 그룹의 연결은 남는다

## 3. 화면 (#284-R3)

#284-S8 N:M 편집 [직접]
- Given 버전 별 분석 탭의 그룹 전체 목록
- When  이번 그룹 줄을 끌어(또는 손잡이를 누른 뒤) 다른 줄의 직전 그룹이나 "리뷰가 들어오지 않은 그룹" 줄에 놓는다
- Then  그 직전 그룹이 이번 그룹 줄 왼쪽에 더해진다. 직전 그룹 옆 풀기 버튼으로 하나씩 풀고, 저장하면 수·막대·레포트가 바뀐다
- Then  레포트는 이어진 직전 그룹을 모두 이름으로 보이고, 리뷰 수 변화와 리뷰 목록은 그 그룹들의 리뷰를 합친다

#284-S9 갱신 확인 창 [직접]
- When  비교 결과가 있을 때 "AI 비교 분석 갱신하기"를 누른다
- Then  "리뷰 그룹을 작업하신 내용이 있다면 분석 과정에서 일부 변경될 위험이 있습니다. 동의하십니까?" 확인 창이 뜨고, 취소하면 아무 일도 없고 동의하면 다시 비교한다
- When  분석 결과가 있을 때 "AI 분석 갱신하기"를 누른다
- Then  그룹이 새로 만들어져 고친 짝·이름·이슈 초안이 사라진다는 확인 창이 뜬다
- When  처음 분석·비교한다
- Then  확인 창 없이 바로 실행한다

## 4. 기존 데이터 (#284-R4)

#284-S10 기존 짝 옮기기 [명령]
- When  배포 뒤 `backend/scripts/add_group_links.sql`을 실행한다
- Then  저장된 비교마다 코드가 같은 두 버전 그룹 쌍이 연결로 들어가고, 다시 실행해도 늘지 않는다

## 범위 밖
- 리뷰 분석을 다시 할 때 고친 그룹(이름·이슈 초안·짝)을 지키는 것. 그룹을 새로 만드는 구조라 큰 변경이다
- 리뷰를 그룹 사이로 옮기거나 그룹을 합치는 편집
- 짝을 고친 뒤 요약을 다시 쓰는 것(#168 범위 밖과 같다)

## 작업 순서
1. 분석 서버 — 고정 짝 받기(`api/schemas/comparison.py`, `domain/models.py`), N:M·고정 짝 검증(`domain/comparison.py`), 프롬프트(`MATCH_SYSTEM`, `render_versions`)
2. 백엔드 — `GroupLink` 엔티티·저장소, `ClusterGroup.linksEditedAt`, 비교 요청·저장·조회(`VersionComparisonReader`·`Writer`), 짝 저장 요청, 다시 분석할 때 연결 지우기(`ReviewAnalysisWriter`), 테스트
3. 화면 — 연결로 짝 그리기·고치기(`features/recruitment/types.ts`·`api.ts`), 그룹 전체 목록·레포트·막대, 갱신 확인 창(`AnalysisToolbar`)
4. 기존 데이터 옮기기 스크립트

## 참고
- 운영 DB는 `ddl-auto: update`라 `group_links` 테이블과 `links_edited_at` 컬럼은 배포할 때 생긴다. 기존 짝 옮기기만 스크립트로 한다
- 백엔드 테스트는 JDK 21이 필요하다. 호스트에 없으면 backend 개발 컨테이너에서 `./gradlew test --tests '*VersionComparison*' --tests '*ReviewAnalysisController*'`로 돌린다
