# 모집 정보 수정 API (#175)

개발자가 모집 관리의 "모집 정보" 탭에서 모집글을 고치는 API. 화면은 영역마다 따로 저장한다(글 정보, 모집 정보, 테스트 정보). 화면 규칙은 [프로젝트 화면 6. 테스트 모집 관리와 탭](../../frontend/project/projects.md#6-테스트-모집-관리와-탭-r106)이고, 도메인 전체에서 정한 것은 [README.md](README.md)에 있다.

시나리오 제목 끝의 태그가 확인 방법이다. `[테스트]`는 백엔드 테스트와 1:1이다(`@DisplayName("#175-S…")`).

## 1. 모집 정보 수정 (#175-R1)

| 동작 | API | 로그인 | 성공 |
| --- | --- | --- | --- |
| 글 정보·모집 정보 수정 | `PATCH /api/v1/developer/recruitments/{recruitmentId}` | 필요 | 200 |
| 테스트 항목 수정 | `PUT /api/v1/developer/recruitments/{recruitmentId}/test-items` | 필요 | 200 |

- 두 API 모두 모집 작성·취소와 같은 `developer/RecruitmentController`에 둔다. 서비스는 모집 작성의 날짜·유형 처리를 다시 쓰려고 `ProjectService`에 둔다
- `PATCH` 본문은 `title`, `description`, `accessUrl`, `softwareTypes`(`web`·`mobile`·`game`·`api` 하나 이상), `conditions`, `selectionMode`, `recruitDeadline`, `submitDeadline`이고 보낸 값만 바꾼다. 글자 수 한도는 모집 작성과 같다. `conditions`를 빈 문자열로 보내면 지운다
- `PUT` 본문은 `{"testItems": [{"id", "title", "description", "required"}]}`이고 보낸 순서가 항목 순서다. `id`가 없으면 새 항목, 목록에서 빠진 기존 항목은 이미지와 함께 지운다. 항목 이미지는 바꾸지 않는다
- 모집글 행을 잠그고(`PESSIMISTIC_WRITE`, 모집 취소와 같은 쿼리) 판단한다. 다른 회원의 모집은 404다

| 규칙 | 이유 |
| --- | --- |
| 종료·취소한 모집은 고칠 수 없다(409 `RECRUITMENT_NOT_EDITABLE`) | 끝난 모집의 글이 바뀌면 참여한 테스터가 본 내용과 달라진다 |
| 지원이 한 건이라도 있으면 선정 방식을 바꿀 수 없다 | 이미 선착순으로 확정된 지원과 선발형 규칙이 섞인다 |
| 모집 마감이 지나면 모집 마감일을 바꿀 수 없다 | 마감된 모집이 다시 열리면 안 된다 |
| 마감일은 미루기만 할 수 있고, 제출 마감은 모집 마감보다 뒤여야 한다 | 참여한 테스터가 안내받은 기간이 줄어들면 안 된다 |
| 선발형은 구독 모집에서만 고를 수 있다 | 모집 작성과 같다 |
| 피드백이 달린 테스트 항목은 지울 수 없다. 내용과 순서는 바꿀 수 있다 | 피드백이 가리키는 항목이 없어진다 |

- 날짜 비교는 한국 날짜로 한다. 보낸 날짜가 지금 저장된 날짜와 같으면 바꾸지 않은 것으로 보고 저장된 시각을 그대로 둔다. 잠긴 칸을 화면이 지금 값으로 보내도 통과한다
- 칸 오류는 400 `INVALID_INPUT`과 `error.fields`(칸 이름은 요청 필드, 항목 줄은 `testItems[0].title`)로 준다. 프론트가 화면 칸 이름으로 바꿔 붙인다
- 카테고리는 바뀐 것만 고친다. 다 지우고 다시 넣으면 Hibernate가 넣기를 지우기보다 먼저 실행해 같은 유형이 겹칠 수 있다

### 테스트 항목 순서
- `test_items`에 `sort_order`를 더했다. 모집 작성은 요청 순서대로 0부터 매기고, 공개 모집글 상세(#113)도 이 순서(같으면 저장 순서)로 준다
- 서버와 로컬 모두 `ddl-auto: update`로 컬럼이 생긴다. 이미 있는 행 때문에 `NOT NULL` 컬럼을 그냥 더할 수 없어 기본값 0(`@ColumnDefault("0")`)을 둔다. 기존 항목은 모두 0이라 저장 순서대로 놓인다

#175-S1 모집 정보 수정 [테스트]
- When  제목·접속 링크·카테고리(웹·모바일)·빈 모집 조건과 하루 미룬 마감일을 보낸다
- Then  200이고 보낸 값만 바뀐다. 설명은 그대로, 모집 조건은 지워지고 유형은 웹·모바일 두 줄이다
- When  카테고리를 모바일만 보낸다
- Then  웹 줄만 지워지고 모바일 줄은 그대로다

#175-S2 선정 방식과 마감일 규칙 [테스트]
- Then  무료 모집을 선발형으로 바꾸면 400, 지원이 있는 모집의 선정 방식을 바꾸면 400이다. 지금과 같은 값은 지원이 있어도 통과한다
- Then  모집 마감·제출 마감을 앞당기면 400, 모집 마감을 제출 마감과 같게 하면 400이고 저장하지 않는다

#175-S3 테스트 중에는 모집 마감일을 바꿀 수 없다 [테스트]
- Given 모집이 마감되고 제출 마감 전인 모집
- Then  모집 마감일을 바꾸면 400("모집이 마감돼 바꿀 수 없어요"), 지금 값 그대로 보내고 제출 마감만 미루면 200이다

#175-S4 종료·취소한 모집과 다른 회원의 모집 [테스트]
- Then  종료·취소한 모집은 두 API 모두 409 `RECRUITMENT_NOT_EDITABLE`이다
- Then  다른 회원의 모집은 404이고 바뀌지 않는다

#175-S5 테스트 항목 순서·내용·추가·삭제 [테스트]
- Given 항목 3개, 마지막 항목에 이미지 1장
- When  [두 번째(이름·필수 바꿈), 새 항목, 첫 번째] 순서로 보낸다
- Then  그 순서로 `sort_order`가 0, 1, 2가 되고, 빠진 세 번째 항목과 그 이미지가 지워진다

#175-S6 피드백이 달린 항목과 다른 모집글의 항목 [테스트]
- Then  피드백이 달린 항목을 빼면 400("피드백이 달린 항목은 지울 수 없어요"), 다른 모집글의 항목 id를 보내면 400이고 바뀌지 않는다
- Then  피드백이 달린 항목도 이름과 순서는 바꿀 수 있다
